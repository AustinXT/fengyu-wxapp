### 3.2 关键根因：共享夹具隔离缺陷（雪崩主因）

实测执行轨迹（日志 253–300 行）清晰还原：

1. **link-1**（第一个用 FY-FIX 夹具开单的 link）执行 → 开单/收款成功、分配保存失败 → cleanup。
2. link-1 之后，**FY-FIX-CARD-01 余额被清零（应 1000→读到 0）、初始流水丢失、FY-FIX-CLIENT-01 在后续 seed 中不可见**。
3. **link-10** 读到错误 baseline=0，其 `afterAll` 又把卡余额"还原"为 0（错误 baseline 固化破坏）。
4. 从 link-10 起，**link-10/11/12/14/16/…/31 等大批 link 因 `FY-FIX-CLIENT-01 / CARD-01 / CT-01 不存在`雪崩式 FK 失败**。

> 注：跑完后查库这些夹具又"都在"（后期 spec 重新 seed 掩盖了中途破坏），且**无任何 spec 含删除 FY-FIX 顾客的字面 SQL**——属测试间共享状态污染 + 事务可见性问题，非显式删除。`cleanupSaleOrder` 本身不删顾客（已核查）。

### 3.3 19 个通过的用例（正面结论）

通过的全部是**不依赖 FY-FIX 开单共享夹具**的类别：

- **admin 配置类**：link-15 提成矩阵快照、link-19 权限即时收回、link-35d OrgTreeSelect、link-53 member-benefits 配置

## 5. Follow-up 建议（按优先级）

1. **【最高】修复 e2e-chains 共享夹具隔离**：这是让业务链路套件可用的前提——即便对齐了商品数据，共享夹具被前序 link 破坏仍会雪崩。方案：每条 link 在 `beforeEach` 重置/自建专属夹具（带唯一前缀），或集中 setup project 在每条 link 前重置 FY-FIX 基线；尤其修复 link-10 `afterAll` 用读取值当 baseline 的逻辑（读到 0 就还原 0）。
2. **【高】定位 link-1 营业额分配保存失败**：手动开单走到分配页保存，看 `saveAllocation` 报错；核查 `commission_rate_matrix` 是否覆盖当前 `product_kind` × 角色 × 市场。本轮唯一真实业务失败。
3. **【高】核查 cron-08 资金不变量违反**：跑 `bun run cron:once --only=paymentInvariants` 看 details 的 invariant 名——真实违反则是生产资金问题，白名单过时则更新测试。
4. **【中】商品域对齐**：product_kind 硬编码改为 DB 动态读取或建标准 e2e 品类数据；重建 12 spec 硬编码的失效 SKU（`c79157…`）+ category，或改 spec 用现存 SKU。
5. **【中】页面 goto 超时复测**：生产 `build && start` 模式复跑 navigation.spec 排除 dev 抖动。
6. **【低】UI 选择器漂移修复**：button-interactions / orders-create-flow / org 失效断言按当前 UI 更新。

### 8.7 全量跑障碍：cron spec 的 module-load 顶层 throw
