### 分层结论

1. **开单 + 收款链路在当前库完全可用** —— link-1 实测顾客搜索、按名选品（"洗-无创纹身"命中）、下单、线下收款确认、积分入账、卡流水全部成功。这推翻了"商品脱节会卡死开单"的预判。
2. **营业额分配保存是一处真实问题** —— 分配比例填 100% 后保存，`sale_allocations` 无写入。`commission_rate_matrix` 仅 16 行，疑提成配置未覆盖当前商品品类（`明星` 等），或分配 action 校验/逻辑问题。**值得优先定位**（详见 §5）。
3. **cron 框架可执行，断言类用例普遍卡在第二条** —— cron-06/08 均为"结构性断言过、注入/白名单断言挂"。要么测试注入口径与当前实现漂移，要么 cron-08 暴露了**真实的资金不变量违反**（需查 details）。
4. **SQL-seed 类 link 被失效 SKU id 系统性挡住** —— `sale_items.sku_id` 有 FK → `product_skus`，而套件硬编码的 `c79157b29c9e974c` 等已全部不存在，seed 必然 FK 失败。

## 5. Follow-up 建议（按优先级）

1. **【高】定位营业额分配保存失败**（link-1）：手动在 admin 开一单走到分配页保存，看 `saveAllocation` action 报错；重点查 `commission_rate_matrix` 是否覆盖当前 `product_kind`（明星/王牌等）× 角色 × 市场。这是唯一实测到的**功能性失败**。
2. **【高】核查 cron-08 资金不变量违反**：跑 `bun run cron:once --only=paymentInvariants` 看 details 的 invariant 名 —— 若是真实违反则是生产数据资金问题；若是白名单过时则更新测试。
3. **【中】页面 goto 超时复测**：在 `bun run build && bun run start` 生产模式下复跑 navigation.spec，排除 dev 编译抖动；若仍超时则定位 `/orders`、`/orders/create` 等页的 SSR 查询。
4. **【中】测试套件与商品域对齐**（治本，工作量大）：
   - 将 product_kind 硬编码（`护理项目/家居产品/充值卡/体验卡`）改为从 DB 动态读取，或在 e2e 库建一套标准 product_kind 数据。
   - 重建 12 个 spec 硬编码的真实 SKU（`c79157b29c9e974c` 等）+ 对应 category，或改 spec 用现存 SKU。
   - 将 FY-FIX 商品类夹具（体验卡/套餐 SKU）脚本化纳入 `seed-fyfix-fixtures.sql`。
5. **【低】选择器/UI 漂移修复**：button-interactions、orders-create-flow、org 的失效断言按当前 UI 更新。
6. **【低】夹具生命周期**：link-32 顾客 FK 瞬时失败提示测试间夹具时序脆弱，建议每条 link 自给自足或集中 setup project 预置。
