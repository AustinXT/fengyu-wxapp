# 系统架构规格书生成

## 核心原则

sys.spec.md 的读者是 Claude Code。它可以随时 `ls`/`cat`/`grep` 读取代码。
**只写 AI 从代码中推断不出的内容。**

### 不要写（AI 可从代码读取）

- 目录结构（`ls` 即可）
- API 路由列表（读 routes/ 目录即可）
- DB schema / ER 图（读 db/schema/ 即可）
- SDK 初始化代码（读 app.ts 即可）
- 组件列表（读 components/ 即可）
- 通用架构知识（分层原则、RESTful 规范、安全分层模型等）
- ADR 模板（仅在有实际决策时记录决策本身）

### 要写（代码中读不出的 WHY）

- **架构拓扑**：环境拆分、网络边界、数据流向、共享资源
- **架构决策及理由**：非显然的技术选型，为什么这样而不是那样
- **集成边界**：外部系统的角色（运行时依赖 / 同步依赖 / 已废弃）
- **约束保障机制**：real.md 每条约束在代码中的具体落地方式
- **跨模块业务流**：仅跨系统边界的编排流程（单模块内的 CRUD 不写）
- **权限模型**：角色×操作矩阵 + 数据隔离规则

## 前置条件

1. 读取 `.42cog/real.md` — 获取硬性约束
2. 读取 `.42cog/cog.md` — 获取实体和业务流程
3. 读取 `.42cog/pm/*.pr.spec.md` — 获取功能需求
4. 浏览代码目录结构 — 了解实际实现状态

## 输出格式

生成文件：`.42cog/dev/sys.spec.md`，目标 ≤150 行，6 节结构：

```markdown
# [项目名] — 系统架构规格书

## 1. 架构拓扑
ASCII 图：端→云函数/API→DB，标注环境隔离和共享资源

## 2. 架构决策
条目式：决策 + 理由（每条 2-3 行）

## 3. 集成边界
外部系统角色表：系统 | 角色 | 访问方式 | 使用场景

## 4. 约束保障机制
real.md 每条约束 → 具体技术实现映射

## 5. 跨模块业务流
仅跨系统边界的流程（ASCII 流程图，标注触发方和数据流向）

## 6. 权限模型
角色×操作矩阵 + 数据隔离规则
```

## 质量检查

- [ ] 每节内容在代码中无法直接推断
- [ ] real.md 的每条约束都有对应的保障机制
- [ ] 无目录结构、无 API 列表、无 schema 定义
- [ ] 总行数 ≤ 150 行
