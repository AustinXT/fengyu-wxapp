## 实现证据
- 【已观察】配置读取会调用 automaticCalendar(null)，失败转为 calendarNotice 仍返回配置；页面显示这个提示。fengyu-admin/src/actions/daily-config.ts:23-24；src/app/(main)/(system)/settings/daily/configuration.tsx:97。
- 【已观察】经营期实际日期优先于规则推算；即使模板规则变化，existing 数据直接被保留。fengyu-admin/src/lib/daily-calendar-auto.ts:70-73。
- 【已观察】自动安排按当前经营月开始，至少准备当前及后两个经营月；requested 可扩展范围，最终仅插入尚未存在的月份。未生成月份与已有相邻经营期不连续或重叠则抛错，且全事务失败。daily-calendar-auto.ts:75-137。
- 【已观察】规则历史按经营期第一天是否达到历史 validFrom 与 mode.effectiveFrom 选择；数据库已经保存的经营期不受这个选择结果重算。daily-calendar-auto.ts:34-49、70-73。
- 【已观察】普通规则保存不改已保存月份，只有增加/修改/删除 monthly 例外才执行 planSpecialMonths；删除例外会拟按普通规则修正该月，而不是无副作用地清空显示。daily-config.ts:156-183。
- 【已观察】已结束月份禁止本页修正；未结束且已有经营/业务可以调整日期，周数变化受到限制，存在当前经营或关联业务时需要影响确认。daily-config.ts:174-175、189-198；98-99。
- 【已观察】现有旧安排编辑入口隐藏在“特殊月份”：选月份点击“设置这个月”，用 arranged(newMonth)[0] 的已保存日期初始化例外，随后保存模式处理例外。cycle-settings.tsx:650-674。一个模式可能覆盖多个市场，而初始化只拿第一个市场的安排；各市场可能存在不同的实际日期，未核实当前是否存在此数据形状。
- 【已观察】日期预览在 dirty=true 时停止请求，并把整张实际日期表替换成“当前修改尚未保存，请先保存该模式，再查看实际日期安排”。cycle-settings.tsx:361-369、758-767。
- 【已观察】dirty 是事件设置的布尔标记，所有 update/replace 都置真，而不是与已保存配置进行内容比较。cycle-settings.tsx:248-259。普通规则变化同样会禁止预览。
- 【已观察】配置中返回 periods 和配置修改日志；日志界面有“准备月份安排”“调整本月日期”等动作标签，但实际日期表没有来源、生成时间或直接修改入口。daily-config.ts:26-57；configuration.tsx:145；cycle-settings.tsx:763-767。
- 【已观察】旧的 prepareMonths 生成动作写日志 daily.period.generate，含 templateSource/monthKey，操作来源 adminApi；新 ensureCalendar 自动生成写相同动作，但来源 dailyCalendar，含 automatic:true。daily-config.ts:328-361；daily-calendar-auto.ts:132-133。两种来源必须区分。
- 【已记录】仓库规范禁止跨端共享云函数工具。admin 和 dailyApi 有独立 daily-calendar-auto 实现，修改共享的日历规则需同步核查另一副本，不可只改一端。用户提供的根 AGENTS.md；fengyu-daily/cloudfunctions/dailyApi/utils/daily-calendar-auto.js。
- 【已观察】当前工作区已有大量未提交的日报修改，包括 db/schema/daily-report.ts、daily-config.ts、日报小程序和配置页面；这轮未动这些文件。来源：本轮 git status --short。

## 证据边界与咨询问题
- 【推断】主要交互问题是普通规则、月份实际安排、特殊月份三者没有清楚区分；对未来无业务且按模板生成的月份采取无条件保留策略，导致用户改规则后仍被旧安排挡住；脏状态又隐藏查看旧安排的途径。依据：上述实现与截图。
- 【已记录】此前答复把生效日期或用户手工设置当成已证实原因，证据不充分。现在已确认阻挡项是数据库已保存经营期；生效规则如何切换属于另一层，不是唯一成因。
- 【已记录】请咨询如何修改产品与代码，让用户能看懂并调整既有安排，优先解释是否应允许未来、未开始、无业务、模板生成月份随普通规则按预览更新，如何处理已开始/已有业务/人工特殊日期，以及自然月切换时真正的边界空档。应保留日期连续性约束并给出可理解的选择，不默认替用户决定哪些天属于哪一期。
- 【已记录】方案需包含清楚入口、旧日期/新日期/来源/作用市场对照、未保存时仍可查看已保存安排、冲突定位、保存影响确认及最小改动范围；不能仅建议手工加特殊月份或仅修改错误文案。
