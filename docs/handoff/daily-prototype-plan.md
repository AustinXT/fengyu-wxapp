# 实施方案

## 状态
已批准实施原型（非生产功能）

## 目标

为新版日报小程序产出一套可与客户确认的原型方案，核心是把日报从“三段自由文本”改造为“一天一份日报 + 顶部目标 + 下方按订单／服务单逐条记录”的结构，并在原型中表达经营周期（不等长、后台可配置、可修改）对日报与目标的约束关系。本轮只产出方案，不改动代码与原型文件。

## 依据事实

以下为事实文件中已核查的内容，方案基于此展开。

**会议中已明确的需求**

- 日报内容需关联订单、服务单，不能只是自由文本（00:01:14—00:01:41）。
- 日报需记录顾客在服务过程中的反馈、产品问题（00:02:39—00:02:49），并在原型中体现与服务单、订单的关联（00:03:04）。
- 结构为“一天一个日报”，顶部填目标，下面每个服务单或订单各成一条记录（00:03:38）。
- 经营月分四个不等长周期，日报与目标都关联周期（00:04:49—00:05:21）；周期由后台提供配置、客户自行填写（00:05:32—00:05:48）。
- 门店、市场层级目标需要填报入口，位置由我方设计后再确认（00:06:59—00:07:42）。
- 分组 PK 属于培训小程序，培训侧需从日报侧取得目标数据（00:11:03—00:12:04）。
- 流程安排为先出日报原型、再与客户确认（00:12:09、00:13:31）。

**旧原型的已观察状态**

- `daily-report/` 下有两个 HTML 原型和两张图片，工作区干净（`daily...origin/daily`）。
- `daily-summary-miniapp-clean.html:1274-1278` 仅有员工、店长、管理层三个角色导航；`1316-1320` 首页、`1344` 填写页、`1346-1357` 本店与总览、`1384` 详情页。
- `daily-summary-miniapp-clean.html:1344` 填写主体仍是“今日行动／今日成长／明日计划”三个必填文本框加指导关系，没有订单／服务单逐条记录。
- `daily-summary-miniapp-clean.html:1258-1262` 经营月为静态示例；`1523-1534` 按自然周及每月 26 日至次月 25 日计算周期，无法表达客户可修改的不等长经营周。
- `daily-summary-miniapp-clean.html:1502-1512,1626-1653` 目标与日报快照用浏览器本地存储演示，没有后台共享配置的效果。
- `daily-summary-miniapp-prototype.html:1435-1494` 同样是三段文本填写页；`1935-1954` 说明第一版只做提交记录闭环。
- 在 `fengyu-admin/src` 中按“经营周／经营月／日报”检索，未发现现成的经营周期配置页面。

**现有业务数据约束**

- `db/schema/service.ts:12-14`：服务单与订单经 `service_items.sale_item_id → sale_items.sale_item_id` 间接关联，服务单主表不存订单 ID。
- `.42cog/cog.md:163`：订单与服务单是多对多关系，单次服务可核销多笔订单项目。
- `.42cog/cog.md:111-115`：销售业绩按款项业绩归属日统计，服务业绩按 `service_date`；日报日期与业务业绩日期不能默认相同。

**本轮资料边界**

- 本轮未修改日报原型或后台代码。
- 上一轮浏览器接口不可用，现有原型的结论依据 HTML 结构与文案得出，未做截图式视觉审查。

**本方案中属于推断而非事实的部分**

- 【推断】原型需分别表达日报日期、订单／服务单日期、经营周期范围及其变更影响，避免用户误以为改周期会改原始业务日期。
- 【推断】“每个服务单或订单分别是一条记录”在多对多关系下需要选定一种主记录粒度，会议未指明具体粒度。
- 【推断】页面结构、角色划分、字段分组等具体设计为本方案提出的设计建议，均未经客户确认。

## 选项与建议

### 一、日报记录的主粒度（核心分歧点）

会议说“每个服务单或订单分别是一条记录”，但数据侧订单与服务单是多对多，必须先定粒度。

- **选项 A：以服务单为主记录**，每条服务单卡片内展开其核销的订单项目。贴合“服务过程中的顾客反馈”这一记录对象，一次服务=一条心得。风险是纯销售、无服务动作的订单无处落。
- **选项 B：以订单为主记录**，每条订单下挂关联服务单。贴合业绩视角，但一次服务核销多笔订单时，员工要把同一段反馈重复填多条。
- **选项 C：混合流水**，日报下的记录条目类型为“服务单”或“订单”二选一，同一天可并存，系统按当日业务数据列出候选，员工勾选后逐条补充反馈。

**建议选 C**，并在原型中把两类条目做视觉区分。理由：它是唯一能同时覆盖“有服务无订单”“有订单无服务”“一次服务多笔订单”三种真实情况的结构，也最接近发言人 2 原话中“服务单或订单”的并列表述。原型中对同一次服务核销多笔订单的情况，默认合并为一条服务单条目、订单项目作为该条目内的明细列出，避免重复填写。

### 二、条目来源：自动带出还是人工选择

会议提到填报时选择服务单（00:02:01），但未定是人工选、系统列出还是两者结合。

- **选项 A：系统按当日业务数据自动列出候选，员工逐条补充**。
- **选项 B：员工手动搜索添加**。
- **选项 C：自动列出 + 允许手动补充遗漏项**。

**建议原型按 C 绘制**，主路径是自动列表（降低填报成本、保证与业务数据对齐），保留“手动添加”次入口。原型中需要明确标注这是设计建议、待客户确认，因为该点在会议中确属未决。

### 三、经营周期的呈现方式

- **选项 A：只读展示**——日报页顶部展示当前经营周期名称与起止日期，配置完全在后台 Web。
- **选项 B：小程序内也可编辑**——与前轮已明确的约束冲突（配置入口在现有后台 Web，客户管理员填写），不采纳。

**建议选 A**。同时原型需替换掉旧版按自然周与每月 26 日至次月 25 日的硬编码算法（`daily-summary-miniapp-clean.html:1523-1534`），改为由一份可配置的周期表驱动，以表达“不等长、可修改”。原型可用一份内嵌的示例周期配置数据模拟后台下发效果，替代当前的本地存储演示（`1502-1512,1626-1653`）。

### 四、目标填报入口的位置

会议明确门店、市场层级目标需要填报入口，但位置需我方设计后确认。

- **选项 A：目标入口独立于日报**，按经营周期设定，店长／市场负责人在各自首页的“周期目标”模块填写；员工日报顶部只读展示所属目标与当前进度。
- **选项 B：目标填在日报顶部**，即每日填报时顺带填目标。

**建议选 A**，并在员工日报顶部保留“当日目标”的只读展示 + 员工个人当日目标的可填字段。理由：经营周期目标是周期级、非每日级数据，每天重填不合理；而发言人 2 说的“顶部填写目标”在员工视角可理解为当日个人目标。这一取舍是本方案的设计判断，需向客户明示并确认。

### 五、角色结构

旧原型只有员工、店长、管理层三个角色（`1274-1278`），但会议出现了“市场”层级目标。**建议扩为员工、店长、市场负责人、管理层四角色**，或确认“市场负责人”是否可并入管理层。此点需客户确认。

### 六、与培训小程序的目标数据衔接

会议已确认分组 PK 在培训侧，培训需从日报侧取目标数据。**建议本轮原型只在目标模块标注“该目标数据供培训小程序分组 PK 读取”的说明性标识**，不在日报原型内绘制 PK 界面，避免越界到培训小程序范围。

## 建议步骤

1. **确认粒度与入口两项设计决策**：先就上述选项一（记录主粒度）和选项四（目标入口位置）与内部对齐，这两项决定整个页面骨架，返工成本最高。
2. **新建原型文件，保留旧文件**：在 `daily-report/` 下新增独立的新版原型 HTML（例如 `daily-report-v2-*.html`），不改动现有两个 HTML 与两张图片，符合“原有内容应保留”的约束。新旧并存便于向客户对比说明改动。
3. **绘制经营周期数据层**：在新原型中内嵌一份示例周期配置（不等长、可修改），所有页面的周期展示与筛选统一读取该配置，替代旧版硬编码日期算法。
4. **绘制日报填写页（核心页）**：顶部为经营周期只读信息 + 当日目标区；中部为当日业务条目列表（服务单／订单条目，自动列出 + 手动添加）；每条目内可填顾客反馈、产品问题等字段；底部保留原有的成长／明日计划类总结字段（待确认是否保留）。
5. **绘制目标填报页**：按角色分别绘制店长、市场负责人的周期目标填报入口，标注供培训侧读取。
6. **绘制列表页与详情页**：日报首页按日期与经营周期组织；详情页展示逐条记录与目标达成情况。
7. **补充原型内的说明性标注**：对所有“我方设计、待客户确认”的点，在原型中以可见批注形式标出，方便后续确认会逐条走查。
8. **整理确认清单**：把下方“需要用户确认的决定”整理成一页，随原型一并提交确认。

后台 Web 的经营周期配置页面本轮不实现——检索显示 `fengyu-admin/src` 中无现成页面，该项属于后端与后台工作，应在日报原型确认后单独排期。本轮仅在方案中记录此依赖。

## 风险与回退

- **粒度选错导致整体返工**：若客户最终要求以订单为唯一主记录，页面骨架需重做。缓解方式是步骤 1 先行确认，并在原型中把条目卡片做成结构相对独立的组件形态。
- **日期语义混淆**（推断风险）：日报日期、服务日期（`service_date`）、款项业绩归属日三者不同（`.42cog/cog.md:111-115`）。若原型不区分，客户可能误以为日报能直接当业绩报表用。缓解方式是在条目卡片上同时显示业务日期，并在原型中加说明。
- **周期修改的影响未定**：周期被使用后允许改到什么程度、历史统计是否重算、已确认工资数据如何处理，会议没有定规则。原型不应表现出“随意可改”的暗示；建议在配置说明处留一条“修改规则待定”的占位提示，待规则明确后再补。回退方式是先只支持“未开始的周期可改”这一最保守表达。
- **误把“日报提交即算薪确认”写进原型**：发言人 1 提出按日确认工资明细再算薪，但发言人 2 提出异议，未达成共识。原型中不得出现算薪确认流程，否则会把未决事项固化为需求。
- **目标字段缺失**：当日目标有哪些指标、各角色各填什么、如何汇总，录音未给出完整字段。原型中的目标字段只能是占位示例，必须标注为待定，不能让客户误认为字段已定稿。
- **视觉层面未验证**：上一轮浏览器接口不可用，旧原型未做截图审查；新原型完成后若浏览器仍不可用，需说明视觉效果未经渲染验证。

回退路径：所有新增内容集中在新文件中，旧原型不动，工作区当前干净（`daily...origin/daily`），任何阶段均可直接放弃新文件回到现状。

## 验证方式

- **结构验证**：对照事实记录逐条核对——是否有“一天一份日报”、顶部目标区、逐条业务记录、顾客反馈与产品问题字段、经营周期关联、门店与市场目标入口、培训侧目标数据标识。
- **周期验证**：修改内嵌示例周期配置为一组明显不等长的周期，确认所有页面的周期展示与筛选随之变化，证明已脱离硬编码日期算法。
- **数据关系验证**：构造“一次服务核销多笔订单项目”的示例数据，确认原型不产生重复填写；构造“有订单无服务单”的示例，确认有落点。
- **日期验证**：构造日报日期与服务日期不同的示例，确认原型分别显示、不混用。
- **保留性验证**：确认 `daily-report/` 下原有两个 HTML 与两张图片未被修改。
- **渲染验证**：浏览器可用时打开新原型走查各页面与角色切换；不可用时明确说明仅完成结构与文案审查。
- **确认验证**：与客户逐条走查确认清单，把每项从“待确认”改为明确结论。

## 需要用户确认的决定

以下每项都会改变原型的画法，且当前证据不足以由我方单方面决定。实施前必须先核实的是前三项（1—3），它们决定页面骨架；其余可在原型走查时确认。

1. **日报记录的主粒度**：采用建议的混合流水（服务单／订单并存、同一次服务多笔订单合并为一条服务单条目），还是以服务单为唯一主记录，或以订单为唯一主记录？
2. **目标填报入口位置**：采用建议的“周期目标独立入口 + 员工日报顶部展示与个人当日目标”，还是每日在日报顶部填写完整目标？
3. **条目来源方式**：系统自动列出当日业务条目 + 允许手动补充（建议），还是纯人工选择？
4. **角色结构**：是否新增“市场负责人”角色，还是并入管理层？
5. **旧版三段文本字段（今日行动／今日成长／明日计划）是否保留**为逐条记录之外的当日总结？
6. **经营周期被使用后的修改规则**：可修改范围、历史统计是否重算、已确认的工资数据如何处理。会议无结论，原型需按此规则绘制提示文案。
7. **目标的具体指标字段**：员工、店长、市场负责人各填哪些值、如何汇总。会议未给出，当前只能以占位示例呈现。
8. **算薪确认是否纳入日报**：会议中存在分歧且未达成共识，本方案默认不纳入，需确认该默认是否正确。
9. **后台经营周期配置页面的排期**：确认本轮仅做日报原型、后台配置页面另行排期，是否符合预期。

## 用户决定
用户已确认采用“系统列出业务条目，员工可手动补充遗漏项”，并要求直接绘制原型。其余未定的业务规则在原型中以“待确认”标注；依 Codex 复核意见，展示后台经营周期配置及其修改影响，但不实现生产后台功能。

## Codex 复核意见

状态：仅复核方案，尚未取得用户对原型实施的选择。

1. 用户已明确“经营周期可以修改”。上文“先只支持未开始周期可改”与该约束冲突，不作为推荐。原型应画出管理员修改已配置周期、影响预览、保存后日报筛选更新与修改记录；已结算工资如何处理另列待客户确认。
2. 用户要拿完整日报方案与凯总沟通。即使本轮不写后台生产代码，原型范围也应包含一张后台 Web 的经营周期配置页及一次修改弹窗，与小程序页面共同演示配置流转。上文“后台页面另行排期”仅适用于代码开发排期，不应排除其原型。
3. `service_items.sale_item_id` 非空（`db/schema/service.ts:85-88`），服务明细本身必须锚定销售明细。上文“有服务无订单”并非当前模型的典型数据形态；应改测“一张服务单对应多张订单”和“一张订单没有服务单”。
4. 算薪确认在会议中有分歧，保持独立待确认。原型可显示“业务记录确认／日报提交”，不应将按钮命名为“确认工资”或暗示提交即算薪。
5. 对客户展示的推荐页面顺序：①后台经营周期列表与编辑影响预览；②员工首页和当日日报；③服务单条目与订单条目各一张；④提交预览及历史详情；⑤店长门店目标；⑥市场负责人市场目标与下钻。旧版三段文本可以放在“可选整日补充”区域，避免挤占逐单记录的主流程。
