# 实施方案

## 状态
草案

## 目标

1. 针对 2026 年 10 月 9 日提出的问题——日报小程序管理层的“组织页面 + 下钻页面”是否应改为 `daily-report/daily-summary-miniapp-v2.html` 的形态——给出一份只读分析结论与明确推荐。
2. 覆盖用户点名的六个界面/能力：组织首页、市场页、门店员工页、个人记录页、日报详情页、人员查找。
3. 区分三类容易被混为一谈的改善：“减少视觉嵌套”“移除重复入口”“真正减少导航点击”，并对每一项给出取舍说明。
4. 对单市场直达门店、多市场进入方式、单门店是否自动跳转、已提交日报快捷入口是否保留，给出建议与边界条件。
5. 明确列出实施前必须先核实的事项，并给出可验收路径与“日期／经营周期上下文”检查清单。
6. 本轮边界：只分析，不修改业务代码、不部署、不迁库；不把未证实的问题表述为既定缺陷。

## 依据事实

### 二、原型侧已观察事实

- 组织页保留“组织架构／人员查找”；总部展示“全部授权市场”及市场行，市场负责人展示市场名称及门店行；门店行与市场行聚合在**一个卡片**内，不同时铺开完整上级树与全部门店（`daily-report/daily-summary-miniapp-v2.html:1705-1707`）。
- 市场行显示门店数量与提交率；门店行显示市场名与已交／应交（同文件 `:1701-1702`）。
- 市场日报页与门店日报页**复用同一范围页面形态**：周期切换、提交概况、一个紧凑列表卡片；市场列表下钻门店，门店列表下钻员工（同文件 `:1715-1717`）。
- 员工进入个人日报记录，再打开日报详情；个人记录按经营月组织，今日入口带锚点；原型在“市场／门店”之间保留周期状态（同文件 `:1641-1654,1871-1873`）。
- 原型仅用总部／单市场两种示例身份与演示组织，**不能证明**任意混合授权账号或不同市场周期均已被覆盖。

### 三、当前实现已观察事实（只读核对）

- 组织树入口与授权门店**同屏并列**；每店一个卡片行（`fengyu-daily/miniprogram/pages/workbench/workbench.wxml:13-14`）。
- 可见节点按 `parent_id` 找根或直接子节点；可见门店按所选节点的全部后代筛选；初始未选节点时**直接列出全部授权门店**（`workbench.ts:104-155`）。
- 点市场进入市场页；点非市场节点在当前页继续展开（`workbench.ts:180-186`）；人员进入个人记录页、门店进入门店页（`:161-163,209-215`，以实际函数为准）。
- 组织页的门店跳转**只带门店标识，不带周期或日期**。
- 市场页含标题与返回、今日／经营周／经营月、概况、一个门店列表卡片；进入门店时传门店标识与周期，**不传日期**（`pages/range/range.wxml:1`、`range.ts:5-25`）。
- 门店页含全授权门店切换、日期、三个周期、概况、每员工一个大卡片的员工日报列表，随后另有一组“已提交日报”列表；比原型多一组列表，但提供直达报告入口（`pages/manager/manager.wxml:1-42`）。
- 门店页接受门店标识与周期，但**日期初始化为今天**；点员工只传员工标识到个人记录页，不带日期或周期；该页无自定义页头，原生导航外观未实测（`manager.ts:26-29,62-64`）。
- 个人记录页独立请求周期列表、默认当前经营月、含概况与日报记录，**不接收来源日期与周期**；因此从历史日期／经营周进入员工时，存在上下文丢失的可能（`pages/history/history.wxml:1-8`、`history.ts:17-23`）。
- 详情页显示姓名／门店、日期、提交时经营周期、冻结经营快照、逐条业务反馈、整日补充、指导关系，通过门店详情接口读取（`pages/detail/detail.wxml:1-5`、`detail.ts:15-18`）。

### 四、多市场与授权约束已观察事实

- 管理层接口要求管理层工作台身份，返回授权范围的组织节点集合；节点必须在该集合内，门店来自授权门店集合并按后代过滤（`cloudfunctions/dailyApi/routes/management.js:6-20`）。
- 市场归属沿祖先节点查找；经营周／经营月范围必须能解析到**唯一市场**，否则明确拒绝——说明跨市场的周期不能直接用同一个默认经营周／月做比较（同文件 `:21-39`）。
- 门店访问按可信授权集合校验；详情只返回本人或授权门店的已提交报告，非本人草稿不可见；**页面隐藏节点不能替代接口鉴权**（`utils/report-scope.js:1-9`、`routes/manager.js:6-17,36-58`）。
- 门店范围通过提交记录的范围解析，未显式传目标门店对应市场；多市场特殊周期是否解析正确需核查，**不能仅靠改样式保证**（`routes/manager.js:17`）。
- 周期列表基于查看者自身的门店归属查询，个人记录页不会向它传目标员工；这可能影响跨市场查看员工时的月份选择，真实数据表现尚未验证（`routes/period.js:39-46`）。
- 交接文档明确“市场→门店→员工→日报”及每接口独立鉴权，**没有**记载“必须把全部组织树搬到首屏”的决策（`docs/handoff/daily-v2-implementation.md:20`）。

### 五、推断与假设（与事实分开，需标注）

- 【推断】同一市场下的门店可能既通过市场入口到达，又通过组织首屏门店入口到达，这解释了“重复感”和用户所述的层级负担。
- 【推断】真实组织节点主要服务于范围计算，逻辑上并不必然要求逐层可见；但该推断成立的前提是产品上仍需保留上级树导航能力。
- 【推断】原型“聚合卡片 + 复用范围页”的收益主要来自**视觉嵌套减少**与**入口唯一化**，不等于每个目标都少点一次；是否需要额外点击取决于单市场／多市场的分支设计。

### 六、未核实项（实施前必须澄清）

- 实际账号数量；总部、多市场负责人、仅授权部分门店、混合市场、独立门店的真实分布。
- 空市场、部门员工、无门店员工的呈现要求（不能凭空引入新业务范围）。
- 各市场是否采用不同经营周期；跨市场日期下钻的实际表现。
- 原生返回路径、滚动位置恢复、较大列表性能与可访问性。
- 门店页原生导航外观、门店页“已提交日报”列表的真实使用频率。

## 选项与建议

### 三个候选路线

| 维度 | 选项甲：完全照搬原型 | 选项乙：沿用原型布局并按真实授权适配（**推荐**） | 选项丙：维持现状，仅局部优化 |
|---|---|---|---|
| 视觉嵌套 | 明显降低 | 明显降低 | 基本不变 |
| 重复入口 | 消除（组织树与门店首屏不再并列） | 消除，但保留可发现的上级导航 | 仍存在重复 |
| 真实减少点击 | 单市场可能减少；多市场不确定 | 单市场明确减少；多市场与现状持平或更清晰 | 不减少 |
| 多市场适配 | 原型未覆盖，风险高 | 按市场拆分为明确分支，风险可控 | 无需适配 |
| 接口改动 | 可能牵动范围与周期解析 | 以页面重组为主，接口改动收敛在周期上下文传递 | 最小 |
| 鉴权安全 | 若误以为前端隐藏即可，风险高 | 明确“前端不承担鉴权” | 无新增风险 |
| 项目风险 | 高 | 中 | 低但收益有限 |

### 推荐

**推荐选项乙：保留原型“单一范围页 + 聚合卡片 + 复用”的组织方式，但按真实授权结构做分支适配**，理由：

1. 代码事实显示，现有接口已按“市场→门店→员工→日报”分层并逐接口鉴权，页面重组不必推翻数据契约。
2. 原型演示身份过于单一，直接照搬会把“单市场假设”固化进多市场场景，触碰“周期必须解析到唯一市场”的既有约束。
3. 视觉嵌套、重复入口、点击次数是三个独立问题，选项乙可以对每一项目标单独取收益，而不必以“完全照搬”承担全部风险。

### 分项取舍建议

- **组织首页**：保留“组织架构／人员查找”入口；把“授权组织范围（市场入口）”与“授权门店大卡片”的并列关系改为**按身份分支**——总部视图先呈现市场行、市场行内聚合门店数量与提交率；单市场身份直接呈现门店行。不再同屏同时铺开上级树与全部门店。
- **是否显示完整组织树层级**：建议不逐层展开，仅在需要时通过上级导航返回；理由是事实层未见“必须逐层可见”的决策记录。
- **市场页**：沿用原型“周期切换 + 概况 + 一个列表卡片”的紧凑形态，替代当前多区块并列。
- **门店员工页**：保留现有“已提交日报”直达入口（它是有价值的能力），但建议作为列表卡片内的次级入口，而不是与员工列表并列的第二组大列表；这样既减少嵌套又不丢直达路径。
- **个人记录页**：接受来源日期与周期作为入参，避免从历史日期／经营周进入时回落到当前经营月。
- **详情页**：基本维持，重点核对提交时经营周期与冻结快照的展示一致性。
- **人员查找**：维持入口与原有能力，不因本次重组而删除。
- **单市场直达门店**：建议支持。当授权范围只解析出一个市场时，组织首页可直接进入门店层，减少一次点击。
- **多市场进入方式**：建议仍以市场行为入口，不合并为跨市场混合列表；理由是多市场周期需解析到唯一市场，混合列表无法安全确定周期语义。
- **单门店是否自动跳转**：建议**不**自动跳转，改为在门店行内直接展开或高亮唯一门店。理由：自动跳转会让返回路径变得不可预期，且滚动恢复行为未实测。
- **已提交日报快捷入口**：建议保留，但降级为卡片内次级入口。

## 建议步骤

**阶段零：只读核实（本轮可做，不改代码）**
1. 拉取真实授权分布：总部、多市场负责人、单市场负责人、仅门店授权、独立门店、混合市场各自的账号样例（去标识化统计即可）。
2. 核实空市场、部门员工、无门店员工的真实存在情况与期望呈现。
3. 核实各市场经营周期是否一致；抽查至少一个跨市场账号在经营周／经营月下的实际解析结果。
4. 核实门店范围解析在多市场特殊周期下的实际返回值；核实个人记录页的周期列表在跨市场查看员工时的实际返回。
5. 在真实账号下核对原生返回路径、滚动位置恢复、较大列表滚动性能。

**阶段一：决策固化（需用户确认后再进入）**
6. 依据阶段零结果，确认组织首页的身份分支规则、多市场入口形态、是否单市场直达、是否保留已提交日报入口。
7. 确认日期／经营周期上下文的传递契约：哪些入口必须携带周期、哪些必须携带日期、返回时如何保持。

**阶段二：页面重组（本轮不实施，仅登记为后续动作）**
8. 组织首页：按身份分支重排，保留人员查找入口。
9. 市场页：收敛为单一列表卡片形态。
10. 门店员工页：员工列表与已提交日报合并为卡片内主次结构。
11. 个人记录页：接入来源日期与周期入参。
12. 详情页：仅做一致性核对，不做结构调整。

**阶段三：核对与回归**
13. 执行“验证方式”中的全部检查项，逐条留痕。

## 风险与回退

| 风险 | 说明 | 缓解 | 回退 |
|---|---|---|---|
| 上下文丢失 | 组织页门店跳转不带周期；门店页日期固定为今天；点员工不带日期与周期；个人记录页不接受来源周期 | 在阶段一先固化上下文契约，再动页面 | 保留原入口与跳转参数，页面回退到当前形态 |
| 多市场周期解析 | 范围必须解析到唯一市场，否则被拒绝；门店范围解析未显式传市场 | 阶段零先核实真实返回值，页面不擅自合并跨市场列表 | 多市场维持按市场分流，不做混合视图 |
| 鉴权被误认为可前端替代 | 页面隐藏节点不等于无权限 | 明确声明前端只做呈现，鉴权仍由接口承担 | 无需回退，属硬约束 |
| 未实测的原生行为 | 原生导航外观、返回位置、滚动恢复均未实测 | 阶段零补测后再定自动跳转策略 | 不启用单门店自动跳转 |
| 列表性能与可访问性 | 较大列表未压测 | 阶段零补测 | 保留分页／分段加载 |
| 把未证实问题当作缺陷 | 现有“重复感”目前仅属推断 | 文档与沟通中统一标注为推断 | 修正表述，不据此下结论 |

## 验证方式

**一、账号矩阵核对**（每条记录：账号类型、可见市场数、可见门店数、期望首屏、实际首屏）

- 总部：应见到全部授权市场及市场行。
- 多市场负责人：应见到其授权市场集合，且各市场内门店不跨市场混合。
- 单市场负责人：应可直接进入门店层。
- 仅门店授权：应直接呈现门店行，不出现空市场。
- 独立门店／无市场归属门店：应有明确呈现，不落入空列表。
- 空市场、部门员工、无门店员工：应有明确且不新增业务范围的呈现。

**二、日期与经营周期上下文检查**（本轮重点）

1. 组织首页 → 门店：核对是否携带周期与日期；若未携带，核对页面回落值是否符合预期。
2. 市场页 → 门店：核对周期是否保留（现状会保留周期、不传日期）。
3. 门店页 → 员工：核对日期与周期是否随跳转保留（现状会丢失）。
4. 从历史经营周／经营月进入员工：核对个人记录页展示的月份是否与来源一致（现状可能回落当前经营月）。
5. 返回路径：逐级返回后，日期与周期是否与进入时一致。
6. 详情页：核对展示的日期、提交时经营周期、冻结快照三者一致。

**三、视觉与交互核对**

- 组织首页不再同屏并列完整上级树与全部门店。
- 同一门店不再同时从市场入口与组织首屏门店入口重复出现。
- 点击次数：对单市场与多市场分别记录“进入目标报告”的实际点击数，与现状对比，用数字说明是否真的减少。
- 原生导航外观与返回按钮位置在真机核对。
- 较大列表滚动性能与可访问性抽查。

**四、验收口径**

- 以上每一项均需有实测记录；未实测项必须显式标注“未实测”，不得以“应当如此”代替结论。
- 本轮结论的适用范围限于分析层面，不代表已完成任何界面验收。

## 需要用户确认的决定

1. 组织首页是否接受“按身份分支呈现”（总部先市场、单市场直接门店），替代当前“组织树入口 + 授权门店大卡片”并列。
2. 是否保留组织树逐层展开能力，还是仅保留返回上级的导航。
3. 单市场账号是否允许直接从组织首页进入门店层。
4. 多市场是否维持按市场分流，不做跨市场混合列表（受“周期需解析到唯一市场”约束）。
5. 是否同意不做“单门店自动跳转”，改为行内直接展开或高亮。
6. 门店页的“已提交日报”入口是否保留（建议保留为卡片内次级入口）。
7. 人员查找入口是否维持不变。
8. 个人记录页是否接受新增来源日期与周期入参（这是修复上下文丢失的关键改动，涉及页面输入契约）。

## Codex 复核与收敛建议

本节是 Codex 阅读咨询方案后的判断；上文保留顾问原始草案，不作为已经批准的实施要求。

1. 当前首屏已直接列授权门店，单市场直接列门店并不必然减少点击。收益是移除重复市场入口与大卡片造成的视觉负担；多市场先市场再门店，比现有直达门店入口可能多一次点击，但范围更清晰。应分别测量，不承诺普遍少点一次。
2. 当前市场页已经是周期切换、概况、一个紧凑门店卡片，不需要把它描述成待替换的多区块并列页面；主要统一页头、范围提示、导航参数与返回状态。
3. 单市场默认直接门店；多市场默认市场列表；仅门店授权默认授权门店列表。判定基于真实授权和门店归属，不基于角色名称或市场节点数量。`utils/scope.js:174-199` 表明仅门店授权未必包含市场祖先；一个市场加额外授权门店也不能误判成仅一个市场。必要归属信息仅用于分组，不扩大可查看市场的数据范围。
4. 单门店保留正常门店行，不自动跳转、不新增行内展开交互；减少页面规则分支，并使返回路径可预期。
5. 门店页以一个员工列表为主；今日已提交员工可提供“查看日报”次级入口，未提交员工显示状态并仍可查看历史记录；周／月进入员工对应经营月记录，不能把任意一份日报当作整个周期。替代第二组重复列表前需确认保留现有直达价值。
6. 个人页继续按经营月归档；从历史日期或经营周进入时定位到该日期所属经营月并突出相应日期／范围，不必强行把个人页变成另一套周统计页。周期应按目标员工／门店解析并独立鉴权，不能只增加前端参数。
7. 日报详情保留提交时快照语义；本次重点是显示与返回路径，不重写详情业务。人员查找保留并检查市场／门店筛选联动、清除不适用门店选择。
