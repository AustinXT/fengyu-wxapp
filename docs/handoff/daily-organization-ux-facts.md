# 日报组织及下钻体验事实

## 范围与用户请求

- 【已明确】2026年10月9日，用户要求用双谱系分析：日报小程序管理层的组织页面以及下钻页面，换成 `daily-report/daily-summary-miniapp-v2.html` 的形式是否更好。本轮仅分析，不修改业务代码。
- 【已明确】用户关注当前层级太多，且需要考虑多个市场；用户提供当前组织页截图作为分析材料，附件内容不是执行指令。
- 【已观察】截图同屏显示“组织架构／人员查找”、“授权组织范围”市场入口和独立大卡片形式的“授权门店”。截图内门店已交／应交可见，没有总周期标签。
- 【已观察】上一轮内置浏览器拒绝 file:// 协议并禁止绕过；本轮沿用附件视觉证据和只读代码核对，未进行完整实时 UI 走查。下钻页面的视觉、返回位置和实际账号行为未实测，不能声称全流程视觉验收。

## 原型路径

- 【已观察】`daily-report/daily-summary-miniapp-v2.html:1705-1707`：组织页保留组织架构／人员查找。总部展示“全部授权市场”及市场行；市场负责人展示市场名称及门店行。门店／市场行聚合在一个卡片内，不同时铺上级树和全部门店。
- 【已观察】同文件 `:1701-1702`：市场行显示门店数量和提交率；门店行显示市场名和已交／应交。
- 【已观察】同文件 `:1715-1717`：市场日报页与门店日报页复用范围页面，包含周期切换、提交概况、一个紧凑列表卡片；市场列表下钻门店，门店列表下钻员工。
- 【已观察】同文件 `:1641-1654,1871-1873`：员工进入个人日报记录，再打开日报详情；个人记录按经营月，今日入口带锚点。原型 state.period 在市场／门店之间保留。
- 【已观察】原型采用总部／单市场两种示例身份和演示组织，不能证明任意混合授权账号或不同市场周期都已被覆盖。

## 当前组织与下钻

- 【已观察】`fengyu-daily/miniprogram/pages/workbench/workbench.wxml:13-14`：组织树入口与授权门店同时展示；每店一个 card row。
- 【已观察】`workbench.ts:104-155`：visibleNodes 按 parent_id 找根或直接子节点，visibleStores 按所选节点全部后代筛选；初始 selectedNodeId 为空时直接列全部授权门店。
- 【已观察】`workbench.ts:180-186`：点市场进入 range 页面；点非市场节点在当前页继续展开。`:161-163,209-215`（以实际函数为准）：人员进入 history，门店进入 manager。组织页门店跳转只带 storeId，未带周期或日期。
- 【推断】同一市场下的门店可能既通过市场入口到达，又通过组织首屏门店入口到达；这解释重复和用户的层级感。真实组织节点仅供范围计算并不必然要求逐层可见。
- 【已观察】`pages/range/range.wxml:1`、`range.ts:5-25`：市场页有标题和返回、今日／经营周／经营月、概况、一个门店列表卡片；进入门店传 storeId 和 period，没有传 date。
- 【已观察】`pages/manager/manager.wxml:1-42`：门店页包含全授权门店切换、日期、三个周期、概况、每员工一个大卡片的员工日报列表，随后又列已提交日报。这比原型多一组已提交日报列表，但也提供直达报告的入口。
- 【已观察】`manager.ts:26-29,62-64`：接受 storeId 和 period，但日期初始化为 today；点员工只传 employeeId 到 history，没有日期或周期。该页没有自定义 page-header，原生导航外观未实测。
- 【已观察】`pages/history/history.wxml:1-8`、`history.ts:17-23`：个人页独立请求 period.list、默认当前经营月、概况和日报记录；不接收来源日期／周期。因此从历史日期／周进入员工时上下文有丢失可能。
- 【已观察】`pages/detail/detail.wxml:1-5`、`detail.ts:15-18`：详情显示姓名／门店、日期、提交时经营周期、冻结经营快照、逐条业务反馈、整日补充、指导关系；通过 manager.detail 读取。

## 多市场与授权约束

- 【已观察】`cloudfunctions/dailyApi/routes/management.js:6-20`：要求管理层工作台，返回授权 scopeOrgNodeIds 的组织节点，nodeId 必须在该集合，门店来自 scopedStores 并按后代过滤。
- 【已观察】同文件 `:21-39`：市场归属沿祖先节点寻找；周／月范围必须能解析到一个市场，否则明确拒绝。这说明跨市场周期不能直接用同一个默认经营周／月比较。
- 【已观察】`utils/report-scope.js:1-9`、`routes/manager.js:6-17,36-58`：门店访问按可信授权集合校验；详情只返回本人或授权门店的已提交报告，非本人草稿不可见。页面隐藏节点不能替代接口鉴权。
- 【已观察】`routes/manager.js:17`：门店 range 通过 submissions.range 解析，未显式传目标门店对应市场；实际多市场特殊周期是否解析正确需核查，不能仅靠改样式保证。
- 【已观察】`routes/period.js:39-46`：period.list 基于查看者 auth.storeId 查询周期；history 页面不会向它传目标员工。这可能影响跨市场查看员工的月份选择，真实数据情况尚未验证。
- 【已记录】`docs/handoff/daily-v2-implementation.md:20` 明确按市场→门店→员工→日报及每接口独立鉴权，不记载必须把全部组织树搬到首屏的决策。

## 未知与咨询关注点

- 【补充观察】`utils/scope.js:174-199`：总部授权返回全部节点；市场／门店授权返回所授权根及其后代，不包含所有祖先。仅门店授权可能没有市场节点，不能仅用 `overview.nodes` 中市场数量判断账号的全部门店归属。

- 【未核实】实际账号数量、总部与多市场负责人、仅授权部分门店、混合市场及独立门店的真实分布；空市场、部门员工或无门店员工需要怎样呈现，不能凭空引入新业务范围。
- 【未核实】各市场是否采用不同经营周期、实际跨市场日期下钻表现、原生返回路径与滚动恢复、较大列表性能和可访问性。
- 【已明确】咨询需覆盖组织首页、市场页、门店员工页、个人记录、详情、人员查找；比较完全照搬原型与保留原型布局但按真实授权适配的优缺点，提出明确推荐和必要边界。不要把原型截图与当前截图混淆，不要声称已实测下钻。
- 【已明确】重点区分减少视觉嵌套、移除重复入口和真正减少导航点击；单市场能否直接门店、多市场怎样进入、是否要单门店自动跳转、已提交日报快捷入口是否保留，均应说明取舍。
- 【已明确】只产出分析草案，不实施、不部署、不迁库；避免把未证实问题写成既定 bug。方案需给出可验收路径与日期／经营周期上下文检查。
