# 实施方案

## 状态
已批准

## 目标

用一个入口解决管理层"看清楚谁没交日报"的问题，同时把"原型图与真机不一致"收敛到一个可验收的版本上。

三条约束贯穿全文：不改已经确定的视觉风格；不新增一批控件；不在没有使用证据的前提下删除已有能力。本轮只分析，不改业务代码、不部署。

具体目标：
1. 让入口第一屏在几秒内说清"这页能做什么"。
2. 统一"市场、门店"的角色分工，消除同一概念在两个标签里各承担一种职责造成的混乱。
3. 先固定一份完整、可比较、可验收的视觉样本（单市场／多市场、门店下钻、员工下钻、每步返回），再讨论删不删功能。

## 依据事实

### 已确认事实：用户侧
- 用户 2026-10-09 要求做双谱系分析，明确本轮只分析，不改业务代码、不部署。
- 用户明确现有视觉风格已确定，反对大改；核心诉求是管理层操作方便、层级少、看起来清楚。
- 用户先前批准"组织顶部同页切换市场、下方更新门店"；随后提出删除两个标签，只保留附件图 2 的员工搜索、市场门店岗位筛选、员工列表；随后又表示"很乱、不知道怎样更清楚"。后一个方案尚未实施，不能视为定稿。
- 用户表达的是使用体验诉求，不是工程诉求，不应要求用户回答工程问题。

### 已确认事实：页面与代码
- 附件图 1 是人员查找模式（顶部两标签＋姓名搜索＋市场／门店下拉＋岗位标签＋员工列表，26 人，每行含姓名、门店岗位、未交齐状态）；附件图 2 是图 1 裁去顶部标签后的下半部分。也就是说，"删掉标签"目前只表现为一次截图裁剪，还不是一套完整的信息架构方案。
- 此前用户提供的组织原型截图：顶部两标签、浅红市场名称条、单白卡紧凑门店行与已交／应交，没有周期切换和提交概况卡。源码当前版本与这张截图并不等同。
- 当前原型 HTML（`daily-report/daily-summary-miniapp-v2.html:1719-1729`）仍有两标签；组织模式含市场选择、今日／经营周／经营月、提交概况、门店卡片；人员模式含搜索、市场门店岗位筛选、员工列表。该文件在 git 中已有未确认的本地修改，既不能当作已确认截图，也不能未经确认直接覆盖。
- 真实小程序组织入口（`workbench.wxml:8-14`）同样保留两标签；组织模式为浅红市场条、门店列表与路径说明，只有今日统计，没有原型里的周期切换与提交概况；人员模式仍是搜索与筛选。两者功能并未对齐。
- 门店下钻页（`manager/manager.wxml:19-42`）有提交概况、每员工独立卡片、另列已提交日报；原型对应位置是提交概况加单卡紧凑人员列表，查看日报入口在行内次级位置。上一轮只改了组织首屏，未改下钻页，路径后半段仍然不一致。
- 个人页（`history/history.wxml:1-8`）按经营月显示个人概况与日报记录。人员入口直达个人页（`workbench.ts:151-152`），门店入口先到管理者页再到个人页，多一次点击，但能先看到店级聚合。
- 总览区块（`home/home.wxml:13-15`）只列待关注市场、门店、员工，即缺交对象，不是完整门店目录。因此删掉组织门店列表后，已交齐门店失去完整对比入口；员工页的门店筛选仍能找到人，但各店横向对比表没有了。
- 组织请求固定今日，按市场对授权门店分组（`workbench.ts:97-111`）；旧服务缺字段时暂时全部授权的门店兼容显示。该兼容只是云端未部署的临时状态，不等于最终按市场的界面。
- 人员模式的市场筛选取总览节点后代集合，门店下拉是全部授权门店，切换市场不联动缩小门店下拉、也不清空旧的门店选择（`workbench.ts:130-143`），可能出现"该市场下无员工"的空结果。
- 组织模式与人员模式各存一份市场选中状态，切换标签不同步市场。
- 仅授权门店时不一定包含市场祖先，不能直接按总览节点数量判断是否单市场；组织新接口按门店祖先归组，只做分组、不扩大权限。
- 跨市场的经营周／月不能共用一个周期；各员工记录沿用各自日报的经营月配置，特殊周期仍需后续验证，本轮不改数据。

### 分析结论（属于判断，不是已验证事实）
- 此前三种形态的口头建议前后不一致，原因是讨论在"入口结构"和"筛选控件"之间来回切换，并非用户的管理任务发生了变化。
- 用户"很乱"的来源更可能是两点：同一组"市场／门店"概念在两个标签里承担了不同角色（一处是筛选条件，一处是导航对象）；加上两个标签名称不直白、筛选状态不同步。标签数量本身未必是主因。

### 假设（未验证，不得当作事实使用）
- 假设一：管理者日常以按门店巡查交报情况为主、找具体员工为辅。若相反，主推荐会改变。
- 假设二：截图中的 26 人只代表当前样本，不代表总部规模；人数放大后员工列表是否可用尚未验证。
- 假设三：标签改名加筛选状态同步能显著降低"乱"的感受，尚未用真实使用验证。
- 假设四：真机与原型不一致，主要源于上一轮只改首屏、未同步下钻页，以及云端未部署，而不是两套代码各自独立演进。

### 实施前必须核实
- 管理者实际使用频率：按门店与按员工哪条是主路径。目前没有任何测量数据。
- 缺少用户确认过的最终连续截图：单市场、多市场、门店下钻、员工下钻、每步返回。当前原型、曾发截图、真实代码不是同一个可验收版本。
- 授权范围形态：实际有多少管理者是单市场、多少是多市场，决定单多市场规则是否需要分支。
- 云端兼容分支下发的时点。在此之前不能把兼容态当作验收样本。

## 选项与建议

### 一条判据，用来打破三选一的循环

**"市场／门店"作为筛选条件，和作为导航页面，是两件不同的事。**
- 作为筛选条件：只在员工列表上方缩小范围，不产生新页面、不产生新返回层级。
- 作为导航页面：门店列表本身可点击、可下钻，多一次点击，但提供店级横向对比。

两者可以共存，但不能含糊地混在一起。当前的混乱正是两种角色同时存在却没有明确分工、也没有共享状态。

### 三个选项独立比较

| 维度 | 甲：保留两标签＋改名＋共享筛选 | 乙：只留员工列表 | 丙：门店列表为主＋独立搜索入口 |
| --- | --- | --- | --- |
| 层级数 | 两个平级切换项，层级不增加 | 最少 | 一个主页面加一个搜索入口 |
| 店级横向对比 | 保留 | 丢失（总览只列缺交对象，无法补出已交齐门店对比） | 保留 |
| 新增控件 | 无 | 无，但删除能力 | 需要一个独立搜索入口 |
| 市场／门店角色 | 两标签各一套，需显式统一 | 退化为纯筛选条件 | 门店是导航对象，市场是筛选条件 |
| 与"不大改视觉"的符合度 | 高 | 高 | 中 |
| 主要风险 | 只改名不同步状态会继续乱 | 无依据删除唯一完整对比能力 | 改动最大，等于重排信息架构 |

### 稳定主推荐：甲

理由，独立于任何一条既有口头推荐：

1. **乙会删掉唯一一处完整门店横向对比。** 总览只列缺交对象，删掉门店列表后，"已经交齐的门店"没有任何位置可看。这是能力损失，而使用频率尚未测量，属于无依据删除。
2. **丙在思路上等价于把门店提升为主的甲，但成本更高。** 它要求新增独立搜索入口并重排层级，与"不大改、不加控件"直接冲突；在还没测出主路径之前先做丙，风险高于收益。
3. **甲改动最小，且直击"乱"的两个真实来源：** 标签名称不直白、两个标签筛选状态不同步。它不删除能力，也不新增控件。
4. **甲是唯一能在不删功能的前提下把两种能力放在同一屏、共享同一套筛选状态做公平比较的方案。** 这正是"固定可比较视觉样本"所需要的。

### 会改变结论的假设

- 若测量显示管理者几乎总是直接找员工、基本不看店级汇总，则乙成立：门店列表可退化为员工页里的一个筛选条件，此时应保留"门店"作为筛选，而不保留门店列表页。
- 若测量显示店级巡查是主路径、且需要更强调门店，则丙比甲合适，因为它把门店升为唯一主页面。即便如此，仍建议先按甲落地并观察，再决定是否升级为丙，以保留回退空间。

### 第一屏具体结构（按甲方案）

自上而下四层，不再出现"组织架构""人员查找"这类看不出内容的名称：

1. **标题行（可选）**：一句话说明用途。
2. **归属选择（全页唯一一处筛选状态）**
   - 单市场：不显示市场下拉，只显示一行纯文本市场名，避免出现只有一个选项的下拉框。
   - 多市场：显示市场选择，默认选中缺交最多的市场；没有缺交时回退到首个授权市场。
3. **视图切换（两个平级、直白命名的切换项）**
   - "按门店看"＝店级汇总：沿用浅红市场条＋紧凑门店行＋已交／应交，不加卡片。
   - "按员工看"＝员工列表：沿用搜索＋岗位筛选＋员工行，保留未交齐状态。
   - 命名避开"组织架构／人员查找"这类抽象词，改为直白描述对象与动作的词（最终用词由用户挑选，见末节）。
4. **内容区**：随视图切换；市场筛选状态在两个视图之间共享，切换视图不重置、不压栈。

统一规则：市场只有一份选中状态；门店下拉只出现在员工视图内部，并随市场联动缩小，切换市场时清空旧的门店选择，避免空结果交叉筛选。

### 点击与返回路径

- 按门店看 → 点门店 → 门店下钻页（店级提交概况＋人员）→ 点员工 → 个人日报页 → 返回回到门店下钻页 → 再返回回到入口，且保留原市场选择与"按门店看"视图。
- 按员工看 → 点员工 → 个人日报页 → 返回回到入口，且保留搜索词、市场、门店、岗位筛选。
- 入口内部切换"按门店／按员工"不产生历史层级：切换不是导航，不压栈，返回键不会在两个视图之间来回跳。
- 门店下钻页的"查看日报"入口沿用现有位置，本轮不改，仅登记为与原型对齐的后续项。

### 单市场与多市场规则

- 单市场判定不能只看总览节点数量：仅授权门店时可能不含市场祖先，应以组织接口按门店祖先归组的结果为准。
- 单市场：隐藏市场选择，第一屏直接进入门店或员工列表。
- 多市场：显示市场选择，默认选中缺交最多的市场，两个视图共用同一份状态。
- 跨市场经营周／月不共用统一周期：本轮不在入口引入周期切换，各员工记录沿用各自经营月配置，特殊周期另行验证，不改数据。

### 当前适用范围

- 只覆盖组织入口第一屏的结构与状态统一，不覆盖门店下钻页、个人日报页的视觉改造。
- 真机当前与原型不一致，且云端兼容分支未部署，本方案不宣称已与真机一致。
- 不涉及权限扩大、不涉及数据口径变更、不涉及经营周期规则变更。
- 本轮不改业务代码、不部署。

## 建议步骤

1. **先固定验收样本，不动功能。** 把"入口→门店下钻→员工→返回"和"入口→员工→返回"两条路径，分别在单市场与多市场授权下截取连续截图，形成唯一一份可比较的验收基线，让当前原型、曾发截图、真机三者先对齐到同一版本。
2. **明确否决"先删功能"。** 在测出主路径之前不实施乙，保留门店列表能力。
3. **按甲落地入口第一屏：** 两个视图改名、统一市场状态、员工视图门店下拉随市场联动并清空旧选择。
4. **同批补齐下钻页与原型的不一致**（提交概况＋紧凑人员列表、查看日报入口位置），避免再次出现"只改首屏、后半段继续不一致"。
5. **部署并核实云端下发**，确认临时兼容分支不再出现在界面上。
6. **观察一段时间后再回答**"按门店还是按员工为主"，届时再决定升级为丙或退化为乙。

关于"真实使用需求未知时，先删功能还是先固定样本"的明确回答：**先固定完整可比较的视觉样本。** 删除不可逆，且会同时删掉判断依据；而"乱"的根因尚未被证实是标签数量。样本固定之后的精简才是可回退的决策。

## 风险与回退

- 风险：把未确认的本地原型修改当成基线并覆盖，会丢失原始版本。回退：所有视觉调整先在截图基线层面确认，改动前明确工作区状态，必要时按版本记录恢复。本轮不动代码，风险暂不发生。
- 风险：统一市场状态后，部分多市场管理者的默认市场与习惯不符。回退：采用简单的"记住上次选择"，或退回各自独立状态，但需接受继续乱。
- 风险：员工视图门店下拉联动后，收窄了原本"先选市场再选任意门店"的用法。回退：联动后保留下拉中的"全部授权门店"选项，允许跨市场查人。
- 风险：只改首屏、不改下钻页，再次出现"前半段清楚、后半段不一致"。回退：下钻页对齐纳入同一批验收，未对齐则整批不通过。
- 风险：真机与原型长期不一致引发验收争议。回退：以真机连续路径为唯一验收对象，原型仅作对照。
- 风险：删除不可逆。回退：本方案不删功能；任何删除都必须等测量结果出来并单独确认。

## 验证方式

- 本轮未重新实测真机或模拟器，未渲染当前原型，结论限于附件、源码与已记录事实，不宣称已完成全流程视觉验收。
- 实施后的验证对象是真机连续路径，不是原型：单市场与多市场各走一遍两条路径，检查返回是否正确保留视图与筛选。
- 检查单市场下不出现单选项下拉；多市场下默认市场为缺交最多。
- 检查员工视图切换市场后，门店下拉联动缩小、旧门店选择被清空、不再出现空结果。
- 检查总览的缺交对象仍能点到对应门店与员工，且门店列表仍是完整对比入口。
- 验证样本规模应大于截图中的 26 人，避免结论只在小样本成立。

### 偏差责任与交付验收方式

- **偏差责任不在用户。** 原型与实现不一致、上一轮只改首屏未改下钻页、云端未部署，都属于交付过程问题：原型在未经确认前被当作规范使用，且同一轮只改了路径前半段，把不一致留在了后半段。
- **验收方式改为连续路径验收：** 以真机截图序列为单位，要求单市场两条路径＋多市场两条路径＋每步返回全部齐全，缺一段即视为未完成。
- **验收前先冻结一版基线：** 未确认的本地原型修改不计入基线，曾发截图仅作参考，真机连续路径为唯一验收对象。
- **每次只改一段路径时，必须同时说明哪些路径仍不一致**，不允许用"首屏已改"代表整体完成。

## 需要用户确认的决定

只确认一项，用非工程问法：

**"管理层打开这个入口时，第一件通常想做的事是哪一件？"**

- 甲：先按门店看各家交报情况，再下钻到人 —— 对应主推荐（保留"按门店看"）。
- 乙：直接找某个员工，基本不看店级汇总 —— 对应"门店只作为筛选条件"的路线（可后续再论）。
- 丙：大部分时候按门店，个别时候直接搜人 —— 同样是主推荐，但可把搜索放得更显眼。

用户只需选甲／乙／丙之一，不必回答任何工程细节。另外，两个视图的最终用词请从直白说法中挑一个（例如"按门店看／按员工看"）。

## 用户决定
2026-10-09 用户明确要求这部分完全按认可的原型设计并实施。批准范围：组织首页及门店下钻一起对齐，保留组织架构/人员查找，市场同页切换，门店和员工采用紧凑单卡列表，员工经营月记录及详情沿用现有页面；不部署。当前 HTML 后续增加的周期/概况不自动加入组织首屏，以已认可的市场条和门店列表截图为准。

## Codex 复核与收敛

- 咨询入口为 Claude Code，实际提供商 api.deepseek.com（DeepSeek），不是 Claude 模型。
- 接受保留两种查看方式但明确名称、共享市场、联动门店的主推荐。理由是当前没有证据表明用户不需要完整门店汇总；该推荐属于可验证设计判断，不是实测结论。
- 不采用“默认缺交最多市场”。默认记住上次合法选择；首次进入用稳定授权市场顺序。避免每次入口变化增加理解负担。
- 顾问说“已交齐门店没有任何位置可看”过于绝对：总览另有范围选择、员工模式有门店筛选，仍能查看相关内容；实际失去的是完整各店提交情况的并列表，不是访问权限。
- 删除前端视图可以用 Git 回退，不属于数据不可逆删除；不应因此引入额外审批。
- 顾问建议额外标题行、重复市场条、跨市场门店选项，不采纳。市场控制只保留一处；所选市场下的“全部门店”只包含该市场授权门店。
- 顾问对下钻改造范围前后不一致。收敛为：本轮只分析；下一轮视觉样本必须展示组织首屏和门店员工页两段，个人经营月记录和日报详情只核对路径，不默认重做。若实施按用户批准的连续截图范围执行，不能用首屏完成代表全部对齐。
- 当前 HTML 已修改版本不是已批准标准，先与曾发截图区分并固定一份预览，再谈落地。视觉必须保留原有卡片、颜色、字体体系。
- 只需要一项业务选择能改变主推荐：日常主要看门店汇总还是直接找员工。无需用户确认工程细节或填一套账号矩阵。用户后续已明确批准按认可的原型实施，以“用户决定”段为准。

## 本轮实施结果

组织首页保留认可截图的市场条与紧凑门店列表，移除路径说明文字；两个视图共用市场选择，人员门店筛选随市场更新。门店下钻采用自定义返回页头、周期切换、提交概况和单卡紧凑员工列表，今日已提交员工行内查看日报，周月进入个人记录；移除重复日报列表及原型没有的门店/日期选择行。个人经营月记录、详情内容未重做。

类型检查与5项页面逻辑测试通过；模拟接口下组织单多市场、人员页、门店页及经营月记录截图已生成并核对，日报详情加载验证到；完整自动化在返回步骤连接超时，未通过完整路径 UI 验收。模拟器项目已关闭清除测试拦截后重新打开，本轮未部署云函数、未提交 Git。
