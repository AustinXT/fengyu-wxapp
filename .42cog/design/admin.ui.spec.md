## 1. 智能分析

### 1.1 应用类型：MPA（多页应用）

**判定依据**：管理后台各模块（组织架构、商品管理、订单管理、权限管理等）相对独立，用户按模块执行离散任务，非持续流式交互。Next.js App Router 天然适配 MPA 路由结构。

### 1.2 导航结构：侧边导航（Side Nav）

**判定依据**：
- 功能模块 10+，层级 2 级（分组 → 模块），顶部导航无法承载
- 管理后台用户主要使用桌面端大屏，侧边导航充分利用横向空间
- 侧边导航支持角色驱动的菜单可见性控制

### 1.3 色彩方案（白红主题，品牌统一）

遵循 `admin.pr.spec.md` §1 定义的色彩方案：

### 3.4 Sidebar（侧边导航）

**展开态**（224px）：图标 + 文字 + 展开箭头
**折叠态**（64px）：仅图标 + Tooltip 显示文字

**菜单分组**：工作台为直达入口；经营业务、客户运营、商品商城、库存管理、组织管理、数据中心、系统管理为可展开二级菜单。展开态采用手风琴，当前路由所属域自动展开；折叠态点击父项显示同一套可访问子项浮层。父级仅在至少一个子项有权限时展示。

**数据中心二级菜单**：销售 `/data-center/sales`、客量 `/data-center/customer`、人效 `/data-center/efficiency`、品项 `/data-center/product`，四项共用 `data_center:dashboard` 权限（无该权限整组消失）。板块必须各占一条路径——侧边栏高亮只比 pathname 不看 query，挂 `?tab=` 会让四个子项同时高亮。裸 `/data-center` 只做跳转：读旧 `?tab=` 深链决定目标板块，无 tab 或非法 tab 落到销售，其余 query 原样带走。切换板块是整页导航，范围/时间/同比环比回落默认（不做 query 透传，侧边栏保持纯 Link）。

**数据中心菜单分段（#367）**：子项按分段小标题组织——**看板**（销售 / 客量 / 人效 / 品项）、**经营明细**（日常数据一览表 `/data-center/daily-overview`、顾客频率表 `/data-center/customer-frequency`、顾客剩余卡项清单 `/data-center/remaining-cards`、经营数据主表 `/data-center/operating-master`）、**员工收入**（员工提成日报 `/data-center/commission-daily`）。原型的「经营数据」「员工收入」一级菜单不单独开，改为本组内的分段。可见子项跨两个及以上分段时才渲染小标题（折叠态浮层同）；同一分段的子项在配置里必须相邻。每页一条路径，高亮只比 pathname。提成明细 `/data-center/commission-daily/detail` 不进菜单，只能从日报下钻，靠前缀匹配高亮日报，面包屑为「数据中心 / 员工提成日报 / 提成明细」（中间一级可点，带 `returnTo` 时回到下钻前的筛选）。路由、标题、权限组合、分段统一登记在 `fengyu-admin/src/lib/data-center/reports.ts`；报表页内容未交付前入口 `menu.enabled=false`（路由可访问、菜单不显示），页面单合入时逐个打开。顾客频率表、顾客剩余卡项清单要求 `data_center:dashboard` + `data_center:customer_detail`，员工提成日报 / 提成明细要求 `data_center:dashboard` + `data_center:staff_commission`（均须由同一条角色授权同时提供），一览表与主表沿用 `data_center:dashboard`。

**进销存二级菜单**：库存查询 `/inventory/stocks`、供应链业务 `/inventory/operations/supply-chain`、市场业务 `/inventory/operations/market`、门店业务 `/inventory/operations/store`、单据中心 `/inventory/docs`、资料配置 `/inventory/skus`。供应链、市场、门店业务页只保留业务办理，不再提供“单据记录”页签；所有单据记录、跨层检索、审计和详情查看统一进入单据中心，通用建单及其审批、收货也在单据中心办理，采购、配货、退货等专用流程仍保留在对应业务页。库存查询仍按库存主体精确筛选，总部、市场、门店各自持有独立库存，选择上级不得汇总下级库存；单据中心改按“总部（供应链）—市场—门店”组织树筛选，单据源端和目标端均记录真实组织节点，选择上级节点时包含其全部后代节点单据。资料配置以页签保留库存商品、供应商、销售商品组成和报货福利 `/inventory/promotions` 四条深链；销售商品组成继续使用兼容路由 `/inventory/sku-mappings`。总部可见三级业务，市场可见市场与门店业务，门店仅可见门店业务；旧业务页的 `view=docs` 与通用 `create` 深链兼容跳转到单据中心，旧库存总览与四类 V1 页面不再作为菜单入口。

**销售商品组成页**：按销售家居商品一行展示最终组成结果，不展示底层映射记录。每个销售 SKU 必须配置至少一个库存商品，每项填写“每件销售商品包含数量”（正整数）；编辑器支持增删组成项，同一库存 SKU 不得重复。列表展示“库存商品 × 数量”和已配置/未配置/含停用商品状态。新订单冻结下单时组成，提货页只展示本次将自动出库的组成与合计数量，不提供库存 SKU 单选器。

**报货福利嵌入规则**：福利方案只由总部供应链维护（新建、修改、停用须由总部 scope 的角色绑定提供 `inventory:supply_chain_master_data_manage`，超级管理员除外），供应链可建全局方案或指定某个市场的专属方案；市场账号只读（#354）。市场汇总报货按整单商品、数量和报货日期自动批量报价，展示标准金额、优惠与应付金额；本市场方案优先于全局方案，组合优先于单品，再按数量门槛、更新时间和方案 ID 排序。具备建单及价格查看权限者可改选当前合规方案，组合方案必须整组切换；提交时服务端重新校验并把最终方案与价格固化为单据明细快照。

**菜单可见性规则**：叶子菜单由 `session.permissions.actions` 与组织范围共同过滤；需要多个无条件 SSR 权限的页面（三级库存业务、单据中心）要求同时具备全部权限，避免菜单可见但进入页面失败。

**系统管理二级菜单**：“系统自检”指向 `/settings/diagnostics`，仅 `system:diagnostics` 可见；旧 `/settings/lakala-diagnostics` 深链跳转到拉卡拉 Tab 并保持菜单高亮。

## 5. 页面规格

### 5.1 登录页 `/login`

**无 Sidebar/TopBar 的独立页面。**

```
┌───────────────────────────────────────────────┐
│                                               │
│              凤御美业管理后台                   │
│              ─────────────────                 │
│                                               │
│         ┌─────────────────────────┐           │
│         │  手机号  [___________]  │           │
│         │  密码    [___________]  │           │
│         │                         │           │
│         │      [登 录]            │           │
│         └─────────────────────────┘           │
│                                               │
│         首次登录？请联系管理员开通权限           │
└───────────────────────────────────────────────┘
```

**交互**：
- 登录按钮点击 → 校验 → 调用 `auth.login` → JWT 存入 httpOnly cookie
- `must_change = true` → 强制跳转修改密码页
- 连续 5 次错误 → 显示"账号已锁定，请 15 分钟后重试"
- 登录成功 → 重定向到 `/dashboard`

### 5.2 强制改密页 `/change-password`

**仅 `must_change = true` 时显示，独立页面。**

| 字段 | 验证 |
|------|------|
| 新密码 | 最少 8 位，含字母+数字 |
| 确认密码 | 与新密码一致 |

### 5.12 开单 `/orders/create`

**向导式表单（Stepper）**：

```
Step 1          Step 2          Step 3          Step 4
选择顾客  ───→  选择商品  ───→  确认订单  ───→  完成
```

**Step 1 — 选择顾客**：
- 手机号搜索框（输入 → 搜索 `client_wechat_users`）
- 搜索结果列表（姓名/手机号/会员等级/归属门店）
- 未找到时可手动输入手机号 + 姓名创建临时记录
- 选中后显示顾客卡片

**Step 2 — 选择商品**：
- 左侧：品项分类导航（按 product_kind 分组 → 分类列表）
- 右侧：商品卡片网格 → 点击选择 SKU → 加入购物车
- 底部购物车栏：已选项目列表 + 数量调整 + 金额小计
- 支持修改实收金额（优惠）

**Step 3 — 确认订单**：
- 订单类型选择（普通/体验/内部/福利活动）
- 支付方式选择（微信/支付宝/线下）
- 指定美容师（Select，可选）
- 优惠券选择（可选，查该顾客可用券）
- 积分抵扣（仅销售单，与优惠券同级并位于商品明细之前）
- 订单明细汇总：应付金额展示扣券后再按行比例分摊积分的最终值
- 确认金额

**Step 4 — 完成**：
- 创建成功提示
- 线下支付 → 显示 [确认收款] 按钮
- 微信支付 → 显示可打印二维码（含小程序码 order_no）
- [查看订单] [继续开单] 按钮

### 5.20 数据中心 `/data-center/{sales|customer|efficiency|product}`（P2）

四个板块（销售、客量、人效、品项）各占一条路径，由侧边栏“数据中心”二级菜单直达，页内不再有板块页签。每个板块内：公共筛选器（范围/时间/同比环比）+ 统计图表 + 数据表格。非法板块段返回 404。

范围筛选：多店权限账号默认选中“全部授权门店”，可继续选择授权市场或该市场下的单家授权门店；单店账号锁定范围，总部账号保留“全部市场”。非总部账号进入时若 URL 无有效范围，入口解析出具体范围后重定向补齐（否则取数会因 `scope='all'` 被拒，生产脱敏后表现为“数据加载失败”）。范围切换同步到 URL，板块内的图表与导出共用同一范围；跨板块切换不保持筛选，回落默认。

图表库选用：**Recharts**（React 原生，shadcn/ui charts 基于此）。

**经营明细报表 `/data-center/{daily-overview|customer-frequency|remaining-cards|operating-master|commission-daily}`（#367 骨架）**：静态段优先于 `[board]`，不扩板块白名单，旧 4 板块路由、筛选 URL 与导出参数不变。页面结构与板块一致：h1 → 公共筛选卡片 → 数据起点提示 → 信息条 → 表格。入口控制流与板块共用（`lib/data-center/entry.ts`：非总部默认 scope 补齐并停在本页、重复 key 规范化、无可查看范围时空态），但报表页的 `tab` 视为页内参数、不当遗留参数剔除。新路由段不加 `loading.tsx`（会让同段 404 页软导航失效），守护递归覆盖整个 data-center 目录。

- **筛选器三种形态**（范围部分与板块共用 ScopeSelect，范围旁显示「共 N 家门店」；交互即时生效，另加「重置」= 回到权限默认范围 + 默认期间并清空页内参数）：
  - 区间型（一览表）：上月（默认）/ 本月 / 近 30 天 / 自定义，URL 键 `period`（`lastMonth|thisMonth|last30|custom`）+ `start`/`end`。上月的上期取前一个自然月；本月的上期为上月同期；近 30 天是相对预设（URL 只存 `period=last30`），上期为紧邻前 30 天；自定义做日历合法性校验（绕开 #308）、最长 366 天，非法或超长回落上月并在控件旁提示。
  - 单月型（频率表、主表、提成日报 / 明细）：`month=YYYY-MM` 下拉，最早 2026-07、最晚本月，默认上月；URL 手传更早月份照常解析，显示空态与数据起点提示，不报错；晚于本月的月份回落默认。
  - 仅范围型（剩余卡项）：不显示日期。
  - 与板块页 `preset/start/end` 语义隔离（`parseReportPeriod` 系列，不改 `parseTimeRange` / `TimeRangePreset`），旧板块不出现新预设。「当月」一律按自然月。
- **数据起点提示**（与 #289 共用 `DataStartNotice`）：所选期间或较上期基期早于 scope 内任一门店在该指标时间轴上的数据起点时，以浅橙警示条列出受影响市场、门店数与起点（悬停看门店明细）。时间轴分业绩（款项归属日期，剔除寄存单）与服务（服务单日期）；按门店取最早日期，没有该轴数据的门店不参与判定。
- **信息条**：表格上方一行数据性标签（范围 · 期间，页面追加条数 / 合计），不加表下大段说明；原型的数据权限横幅本期不做。
- 视觉用 admin 设计令牌（品牌色 #C0322A），不用原型蓝色。
- **顾客剩余卡项清单**（#371）：指标卡 6 张（范围全量）→ 搜索框（姓名 / 门店 / 会员等级 / 完整手机号）+「全部顾客｜只看有剩余」+ 图例 + 导出 → 矩阵表（左冻结 门店｜顾客（姓名 + 脱敏电话）｜会员等级，中间按一级分组的二级品项列，右冻结「剩余次数」，表尾合计按全部筛选结果）。单元格四态：✓ 有剩余（强调）/ 待付清（浅橙底，沿用 badge 配色）/ 已服务完（弱灰字）/ 未买过（留空），在途退款加「冻」角标，悬停看次数说明。服务端分页（20/50/100，默认 50），只有「剩余次数」列可排序。口径见 `notes/references/metrics.md`「顾客剩余卡项清单」。
- **顾客频率表**（#370）：单月型。指标卡 9 张按 3 × 3 排（范围全量）→ 搜索框（姓名 / 完整手机号）+「全部顾客｜只看有到店」+ 图例（✓ 当日到店含消费到店，下方为当日消费；周末浅底；交易跟着顾客走）+ 导出 → 矩阵表（左冻结 姓名｜电话（脱敏）｜会员等级｜所属门店，中间「本月日历」1~N 日列、周末浅底，右冻结「本月合计」到店次数｜消费合计，表尾合计按全部筛选结果）。单元格：✓ + 当日金额 / 只打 ✓ / 只显示金额（负数红）/ 留空，悬停看当日消费、消耗、服务项目、发生门店。服务端分页（20/50/100，默认 50），两列汇总可点表头排序。口径见 `notes/references/metrics.md`「顾客频率表」。

## 6. 状态管理

### 6.1 认证状态

```typescript
// 服务端：Next.js middleware 校验 JWT cookie
// 客户端：通过 Server Component 获取 session

interface AuthSession {
  employeeId: string
  name: string
  phone: string
  roles: Array<{
    role: 'admin' | 'manager' | 'finance' | 'hr' | 'product' | 'customer_mgr'
    scopeId: string
    scopeType: '总部' | '市场' | '门店'
  }>
  permissions: {
    actions: string[]     // 如 ['sale_order:create', 'employee:list']
    scopeStoreIds: string[] // 可访问门店列表
  }
}
```

### 6.2 页面数据获取策略

| 场景 | 策略 | 理由 |
|------|------|------|
| 列表页数据 | Server Component + `searchParams` | SSR 首屏快，URL 参数驱动筛选/分页 |
| 详情页数据 | Server Component | SSR |
| 表单提交 | Server Action | 避免暴露 API 端点 |
| 实时状态（同步进度） | Client Component + SWR 轮询 | 需定期刷新 |
| 下拉选项（门店/部门/员工） | Server Action + 客户端缓存 | 频繁复用 |

### 6.3 客户端状态（Zustand，仅限非持久化 UI 状态）

```typescript
// 侧边栏折叠状态
interface UIState {
  sidebarCollapsed: boolean
  toggleSidebar: () => void
}

// 开单向导临时状态
interface OrderCreateState {
  step: 1 | 2 | 3 | 4
  customer: Customer | null
  cart: CartItem[]
  orderType: string
  paymentMethod: string
  // actions...
}
```

> **原则**：业务数据通过 Server Component/Server Action 获取和操作，Zustand 仅管理纯 UI 交互状态。不在 localStorage 中缓存业务数据。

## 7. 交互模式

### 7.1 加载态

## 9. 可访问性（WCAG AA）

| 要求 | 实现 |
|------|------|
| 颜色对比度 | 主色 `#C0322A` 在白色背景上对比度 ≥ 4.5:1（实测 6.2:1 ✅） |

| 加载反馈 | Skeleton 使用 `aria-busy`；操作按钮 disabled 时含 `aria-disabled` |
