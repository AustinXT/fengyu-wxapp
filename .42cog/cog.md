以"商品电商 + 后台管理"为主线描述凤御微信小程序的核心概念模型。实体按电商业务流排序：门店(组织) → 商品目录 → 订单交易 → 履约核销 → 用户身份 → 分账。

---

<cog>
本系统的核心业务流为：
  门店（组织归属）→ 商品目录（卖什么）→ 订单（交易记录）→ 履约/服务单（到店核销）→ 营业额分配（分账）
辅助流程：预约（到店时间协调）、门店解绑（组织变更）、操作日志（审计追踪）
核心角色：顾客（买方）、manager（经营管理）、finance（财务只读）、hr（员工管理）、product（商品管理）、staff（一线执行）
销售单据 + 支付流水模型：sale_orders 承载销售单 / 内部单 / 转换单三类，回款与退款下沉至 sale_order_payments（sop）通过 change_type 区分
</cog>

<门店>
- 组织架构的核心节点，所有业务数据按门店归属
  - 组织层级：邻接表层级树，品牌总部 → 市场 → 门店；部门可挂在任意层级
  - 部门：美容部、养生部、推广部、品项部（各有独立的营业额分配规则）
  - 门店解绑流程：顾客发起解绑申请（待处理 → 已通过/已拒绝/已取消）→ 店长审批 → 解除绑定
  - 门店详情：封面图、环境图、地理坐标、营业时间、停车信息等（员工端维护）
</门店>

<商品目录>
- **商品**：商品概念层，如"蜜语生玑精华护理疗程"
  - 商品类型（product_kind）：**完全数据库驱动**，由 `product_categories WHERE productKind IS NULL AND isValid=true` 行决定。运营在 admin "品项分类 → 一级品项管理" 内增删；4/17 会议要求护理项目→招牌/王牌/明星拆分即在此操作。代码层不再硬编码字面量列表。
  - 一级行带 capability 列：`displayColor`（前端 tag 颜色）、`displayIcon`、`requiresShengmeiFlag`（SKU 表单是否显示"是否生美"开关）。"卡 vs 非卡"识别已下沉到 SKU 级 `isExperience` / `isRechargeCard`（2026-05-18 product-domain cleanup）
  - 品项分类：如"蜜语生玑"，作为商品列表左侧一级导航
  - 上下架由有效期日期控制，无独立开关
  - 可标记为套餐（套餐的 SKU 是其组成部分）

- **商品规格**：规格 + 价格层
  - 产品类型（product_type）：`疗程卡`（按次核销，session_count≥1，含原"单品"=1 次）| `家居产品`（支付即完成，不走到店核销；2026-04-25 由"院装产品"重命名）
    - 2026-05-21 单品合并：原"单品"（一次核销）并入疗程卡（session_count=1），枚举从 3 值精简为 2 值
  - 开单时价格快照到销售明细
</商品目录>

<订单>
- **订单**：交易记录，一切后续流程的源头
  - 状态：`待支付` → `待确认收款` → `已支付` → `已完成`；异常分支 `支付失败`（店长可重置）；终态 `已关闭`；退款专用 `待审批`
  - 类型（sale_order_type）：`销售单` | `内部单` | `转换单`（回款 / 退款下沉至 sale_order_payments.change_type）
  - 来源：`client`（顾客自助下单）| `staff`（员工开单 → 生成二维码 → 顾客扫码支付）
  - 支付方式：`微信` | `支付宝` | `线下`
  - 待支付订单唯一：已注册顾客全局唯一，未注册顾客按手机号+门店唯一
  - 销售单据 + 支付流水模型：回款 / 退款 = sale_order_payments 行（关联原 sale_order_id），转换单仍是独立 sale_orders 行通过 ref_sale_order_id 引用原单

- **销售明细**：SKU 维度的购买行，是核销锚点

- **关键业务规则**：
  - 家居产品：支付即完成，不走服务单
  - 疗程卡（含原单品=1 次卡）：按次核销流程
  - （2026-05-21 单品合并后，原"单品支付后 1 年自动到期"规则已移除）
</订单>

<服务单>
- **服务单**：到店履约/核销记录
  - 状态：`待服务` → `服务中` → `已完成`；可取消（`已取消`）
  - 与订单无直接关联，通过服务明细间接关联销售明细（订单 ↔ 服务单 = N:N）
  - 跨订单核销：同一次到店服务可消费来自不同订单的项目
  - 次数扣减仅在"服务中 → 已完成"时执行，取消不扣次数

- **服务明细**：核销行，关联销售明细（核销锚点）
  - 扣减后若剩余次数归零，自动关闭关联的待确认/已确认预约
</服务单>

<用户>
- **顾客**：微信身份 + 顾客档案合一
  - 绑定手机号后与顾客档案关联（合并行）
  - 可绑定门店、指定美容师（营业额分配默认人员）
  - 手机号补全机制：员工以手机号开单 → 顾客后续注册绑定手机号 → 历史订单自动关联

- **员工**：微信身份 + 员工档案合一
  - 绑定手机号后自动关联员工档案
  - 角色由 RBAC 权限表决定，无记录时降级为最低权限（仅操作自己相关记录）
  - 登录时聚合所有角色和权限，前端据此控制 UI 可见性
  - 两端 openid 完全独立（不同 appid），用户表不共享
</用户>

<权限>
- RBAC + Scope 模型
  - 6 角色：`manager`（经营管理）| `finance`（财务只读）| `hr`（员工管理）| `product`（商品管理）| `staff`（一线执行）| `customer_mgr`（顾客管理）
  - 3 域级别：`总部`（全局无过滤）| `市场`（市场区域）| `门店`（单门店）
  - 11 功能模块：workbench / sale_order / allocation / service / appointment / customer / product / employee / finance / store / permission
  - 一人多角色 + 一角色多域：同一员工可有多条记录
  - 提成比例矩阵：组织 × 订单类型 × 角色类型 × 销售分类 × 金额阶段 → 提成比例
</权限>

<营业额分配>
- 销售明细级业绩归属
  - 时机：订单"已支付"后由店长操作分配，可重新分配（覆盖式更新）
  - 订单关闭/支付失败时作废
  - 退款业绩为负数，转换/回款保持正数

- **部门分配规则**：
  - 同部门：分配总额 <= 实收金额
  - 跨部门：各部门独立计算，总额可达实收 N 倍
  - 指定美容师自动分配：支付回调时自动创建 100% 分配
</营业额分配>

<业绩日期归属>
- `sale_order_datetime` 是原始交易事实，永不因统计周期改写
- `sale_orders.performance_attribution_date` 是首次支付的统计归属日，默认为订单上海自然日
- 回款、储值卡抵扣和退款各自在 `sale_order_payments.performance_attribution_date` 记录归属日，入账时默认取 `paid_at` 上海自然日
- 系统管理员、店长、财务可在订单详情修改一次；无操作时限，可选值为原始订单日前后 7 天（含边界）
- 款项归属日也只能修改一次，范围为各自 `paid_at` 上海自然日前后 7 天；首次支付仍只能随订单调整
- 服务业绩固定按 `service_date`
</业绩日期归属>

<预约>
（辅助流程，类似电商的"预约送货时间"）
- 状态：`待确认` → `已确认` → `已完成`；可取消（`已取消`）；超时/次数归零自动 `已关闭`
- 可选关联销售明细（指定消费哪个订单行）
- 到店签到：记录时间，不改状态
- 一条预约最多关联一张服务单
</预约>

<rel>
实体关系（概念层，指导 schema 设计）：

**组织域**
- 组织节点 → 父组织节点：自引用层级树（品牌总部 → 市场 → 门店，部门可挂在任意层级）
- 门店 — 组织节点：1:1 扩展（门店是 type='门店' 组织节点的详情补充）

**商品域**
- 品项分类：按商品类型（product_kind）分组
- 商品 → 品项分类：N:1（一个分类下多个商品）
- 商品规格 → 商品：N:1（一个商品可有多个规格/SKU）

**用户域**
- 顾客 → 门店：N:1（绑定门店，可变更）
- 顾客 → 员工：N:1（指定美容师，用于营业额分配默认人员）
- 员工 → 门店：N:1（所属门店）
- 员工 → 组织节点(部门)：N:1（所属部门）
- 顾客端和员工端 openid 完全独立（不同 appid），两张用户表不共享

**订单域**
- 订单 → 门店：N:1
- 订单 → 顾客：N:1（可为 null，手机号开单时顾客未注册）
- 订单 → 员工(开单人)：N:1
- 订单 → 员工(指定美容师)：N:1（用于自动分配）
- 订单 → 订单：N:1（回款/转换/退款 引用原销售单，销售单此字段为空）
- 销售明细 → 订单：N:1
- 销售明细 → 商品规格：N:1（开单时价格快照到明细行）
- 销售明细 → 销售明细：N:1（转换转出/退款转出 引用原购买行，购买行此字段为空）

**服务单域（核销）**
- 服务单 → 门店：N:1
- 服务单 → 顾客：N:1
- 服务单 → 员工(负责美容师)：N:1
- 服务单 → 预约：N:1（可选关联，一条预约最多对应一张服务单）
- 服务明细 → 服务单：N:1
- 服务明细 → 销售明细：N:1（核销锚点，跨订单核销的关键连接）
- 服务明细 → 员工(操作人)：N:1
- **核心 N:N**：订单 ↔ 服务单无直接关联，通过 服务明细→销售明细→订单 间接关联，支持同一次到店跨多笔订单核销

**预约域**
- 预约 → 门店：N:1
- 预约 → 顾客：N:1
- 预约 → 员工(美容师)：N:1
- 预约 → 销售明细：N:1（可选，指定消费哪个购买行）

**营业额分配域**
- 分配 → 销售明细：N:1（明细级归属，非订单级）
- 分配 → 员工：N:1
- 同一销售明细可分配给多个员工（跨部门时各部门独立计算）

**权限域**
- 权限角色 → 员工：N:1
- 权限角色 → 组织节点(域)：N:1（域级别：总部/市场/门店）
- 一人多角色 + 一角色多域（同一员工可有多条记录）

**提成域**
- 提成比例矩阵 → 组织节点(市场)：N:1
- 矩阵维度：组织 × 订单类型 × 角色类型 × 销售分类 × 金额阶段

**券域**
- 券模板：定义规则（类型、面额、适用范围、有效期）
- 用户券 → 券模板：N:1
- 用户券 → 顾客：N:1
- 用户券 → 订单：N:1（使用时关联，下单原子校验防重用）

**门店解绑域**
- 解绑申请 → 顾客：N:1
- 解绑申请 → 门店(原门店)：N:1
- 解绑申请 → 员工(审核人)：N:1（可选，审批后写入）

**操作日志**
- 操作日志 → 员工(操作人)：N:1
- 操作日志 → 组织节点：N:1（可选）
- 日志以 action(module.method) + target(type+id) 定位操作对象
</rel>
