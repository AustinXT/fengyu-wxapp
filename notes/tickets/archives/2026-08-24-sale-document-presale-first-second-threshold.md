## 0 一句话目标

销售单不再只按顾客当前会员身份粗分“售前/售后”，而是按顾客第几次完成达到会员阈值的消费，冻结为“售前一次 / 售前二次 / 售后”；服务单分类保持原样。

## 1 名词与判定规则

### 1.1 阈值

- 使用现有系统配置 `new_member_threshold`，当前默认值为 **1990 元**；禁止在各端硬编码 1900/1990/1999。
- 判定必须读取与会员升级相同的配置源；配置缺失或非法时沿用该配置模块的统一默认与告警策略。

### 1.2 达标消费

- “一次销售”指顾客第一次发生达到阈值的有效消费，**本次正在结算的订单包含在次数统计内**。
- “二次销售”指顾客第二次发生达到阈值的有效消费，本次订单同样包含在内。
- 达标次数以成功入账后的销售单为单位；同一订单多次回款只算一次。
- 建议基准口径：单张销售单净有效消费达到阈值即记一次；若业务最终要求“累计跨单凑满阈值”，实施前必须另行确认，不能由开发自行切换算法。

### 1.3 分类状态机

| 当前单结算后达标次数 | `document_type` | 说明 |
|---:|---|---|
| 0 | `售前一次` | 尚未出现达标消费，仍处于首次转化阶段 |
| 1 | `售前一次` | 当前单是第一次达标消费，包含当前单 |
| 2 | `售前二次` | 当前单是第二次达标消费，包含当前单 |
| ≥3 | `售后` | 已完成两次达标销售后的后续消费 |

订单创建时可先写预测值，但最终权威快照必须在首次成功入账事务内确定，避免待支付单占用次数。订单后续回款不得重算分类。

### 1.4 纳入与排除

- 纳入：`sale_order_type='销售单'` 且进入有效支付状态的订单。
- 排除：内部单、转换单、寄存单、充值单、待支付、支付失败、已关闭订单。
- 退款不重排其他历史订单的 `document_type`；若当前订单全额退款，其已冻结分类保留用于审计，但后续“达标次数”是否继续计入应与会员有效消费口径共用同一净额算法。
- WorkFine 历史单参与次数前，必须验证其金额和状态字段能满足同一有效消费口径。

## 2 当前实现与冲突

- `db/schema/enums.ts` 当前 `document_type` 仅有 `售前/售后`。
- client、staff、admin 的开单路径当前明确使用“下单时会员客→售后，否则→售前”。
- 2026-07 的代码和测试曾主动删除“金额达到阈值即售后”的旧分支，因此本 ticket 是新决策，不是简单恢复旧逻辑。
- 服务单另有 `service_order_type`，继续维持 `售前/售后`，严禁顺手扩展为三值。

## 3 L0–L10 传播清单

- **L0** `db/schema/enums.ts`：将销售订单 `document_type` 扩展/迁移为三值；确认不会误改服务单枚举。
- **L1** `db/schema/order.ts`：确认 `sale_orders.document_type` 类型；`db/schema/service.ts` 不变。
- **L2** 新迁移：存量 `售前` 的回填策略必须基于历史达标次数顺序计算，不能全部粗暴改成 `售前一次`；`售后` 也需重算或记录保留理由。
- **L3** 检查 WorkFine 迁移、会员回填及修复脚本中的 `document_type` 字面量。
- **L4–L6** 更新 admin 类型、actions、seed。
- **L7** 更新 clientApi/staffApi 的订单、充值卡、转换、寄存等创建路径；排除路径应写明确常量。
- **L8–L9** 更新订单详情、顾客疗程卡、服务创建等只读展示标签。
- **L10** 更新 admin/client/staff 单测、L2 smoke、历史 fixture 和 snapshot。

## 4 并发与幂等设计

1. 在顾客维度取得事务级 advisory lock，锁内查询既有达标销售单次数。
2. 当前订单首次成功入账时，将当前单纳入计算并写入最终 `document_type`。
3. 使用支付事件/订单状态 CAS 保证同一订单只有第一次入账能冻结分类。
4. 两张同顾客订单并发结算时必须得到连续且唯一的第 N、N+1 次结果。
5. client 微信支付、staff 线下确认、admin 确认收款等所有结算路径调用同一算法的各自独立副本，并用 snapshot 守护一致性；不得建立跨端共享目录。

## 5 验收用例（DoD）

- [ ] 顾客无历史达标单，本次低于阈值 → `售前一次`。
- [ ] 顾客无历史达标单，本次恰好等于阈值 → `售前一次`。
- [ ] 已有一次达标单，本次第二次恰好达标 → `售前二次`。
- [ ] 已有两次达标单，后续销售单 → `售后`。
- [ ] 一张订单分多次回款，只增加一次达标次数。
- [ ] 内部/转换/寄存/充值单不增加达标次数。
- [ ] 两张订单并发结算不会都判为“售前一次”或“售前二次”。
- [ ] 退款不改写其他历史订单分类，后续次数计算符合统一净额规则。
- [ ] admin、clientApi、staffApi 对同一 fixture 得出一致分类。
- [ ] 服务单仍只允许 `售前/售后`。
- [ ] 完成迁移 dry-run 统计：三类存量数量、异常订单和抽样明细。
- [ ] admin TypeScript、三端单测、跨端 snapshot 和相关 L2 smoke 全部通过。
