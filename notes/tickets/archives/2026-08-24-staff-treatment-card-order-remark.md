## 0 一句话目标

员工查看顾客疗程卡或从疗程卡创建服务单时，能看到每张权益对应的来源订单备注，避免疗程卡合并展示后丢失业务上下文。

## 1 已确认规则

1. 备注来源唯一为 `sale_orders.remark`，通过 `sale_items.sale_order_id` 关联；不能用疗程卡自身备注替代。
2. 同一订单下多个疗程卡行展示同一订单备注；不同来源订单的备注不得合并或串单。
3. 空备注不展示占位块，避免页面噪声。
4. 备注为只读业务信息，本 ticket 不增加员工修改订单备注能力。
5. 创建服务单时“带入”定义为在选卡/确认区域只读展示来源订单备注，不自动写入 `service_orders.remark`，避免把销售备注变成护理记录。
6. 顾客端已有展示逻辑保持不变。

## 2 当前实现与缺口

- 顾客端 `clientApi/routes/order.js` 已查询并返回 `orderRemark`，疗程卡页面已展示。
- 员工端 `staffApi/routes/customer.js` 的顾客订单/疗程卡查询未选择 `o.remark`。
- `packageCustomer/customer-detail` 的疗程卡类型、分组和 WXML 未承载订单备注。
- 顾客详情批量创建服务单的 preload 未携带备注；`packageService/service-create` 因而无法展示。

## 3 API 契约

员工端疗程卡/订单返回项新增：

```ts
orderRemark: string | null
```

- SQL 必须显式选择 `o.remark AS order_remark`，继续使用参数化查询。
- 映射层统一 trim；空字符串映射为 `null`。
- 不返回其他订单内部字段，不扩大数据权限。
- 按既有 scope 查询结果展示，不能因备注需求放开跨店权限。

## 4 前端交互

### 4.1 顾客详情 → 疗程卡

- 在订单号附近展示“订单备注：{内容}”。
- 最多显示合理行数，超长内容允许换行/展开，但不得横向溢出。
- 合并卡片若含多个来源订单，必须按来源订单分组展示，不能只取第一条备注。

### 4.2 创建服务单

- `customer-detail.ts` 写入 `_serviceCreatePreload` 时携带 `orderRemark`。
- `service-create.ts` 类型和初始化映射接收该字段。
- 在已选疗程卡行或确认区显示只读订单备注。
- 手工进入服务创建页、没有 preload 时兼容 `null`，页面不得报错。
