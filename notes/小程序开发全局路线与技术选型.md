# 凤御美业小程序 - 技术路线与选型（定稿）

## 技术路线：原生微信小程序 + 腾讯云 CloudBase

本项目采用**微信原生开发 + CloudBase 云开发**作为唯一技术路线。以下为确定选型及理由。

---

## 1. 技术栈总览

| 层 | 选型 | 说明 |
|---|---|---|
| 小程序前端 | **原生微信小程序 + TypeScript** | 仅做微信端，原生性能最优、平台能力完整覆盖 |
| UI 组件库 | **Vant Weapp** | 商城组件成熟，社区生态好，开箱即用 |
| 后端运行时 | **CloudBase 云函数（Node.js）** | 免运维、自动扩缩容、内置微信鉴权 |
| 数据库 | **CloudBase 文档数据库（NoSQL）** | 内置实时推送能力，完美支撑日历 5 秒联动 |
| 实时通信 | **CloudBase 实时数据推送** | 数据库 watch 监听，无需自建 WebSocket |
| 文件存储 | **CloudBase 云存储** | 图片、协议文件等静态资源 |
| 认证 | **CloudBase 微信登录** | 一行代码完成小程序登录，自动管理 session |
| 包管理 | **npm** | 微信开发者工具原生支持，无需额外工具 |
| 仓库组织 | **两个独立仓库** | 客户端和员工端各一个仓库，结构清晰 |
| 发布 | **微信开发者工具 + miniprogram-ci** | 标准发布流程 |

---

## 2. 选型理由

### 为什么选原生小程序而非 Taro/uni-app

- 本项目仅做微信端，无多端复用需求
- 原生开发零框架损耗，首屏加载更快
- 平台新能力（实时数据推送、订阅消息等）第一时间可用，无需等框架适配
- CloudBase SDK 与原生小程序深度集成，跨端框架反而增加适配成本

### 为什么选 CloudBase 而非 Nest.js + MySQL

- **实时推送内置**：CloudBase 文档数据库支持 `watch()` 实时监听，订单写入后员工端日历自动更新，天然满足「5 秒联动」核心需求，无需自建 WebSocket
- **微信登录零成本**：`wx.cloud.callFunction` 自动携带用户身份，无需手写登录态管理
- **免运维**：无需管理服务器、数据库实例、SSL 证书、负载均衡
- **快速交付**：云函数即写即部署，适合小团队快速迭代 MVP
- **成本可控**：按调用量计费，MVP 阶段成本极低

### 为什么选 Vant Weapp 而非 TDesign

- 商城类组件更完整（商品卡片、价格、下拉刷新、搜索等）
- 社区用户量大，常见问题搜索即得
- 与原生小程序兼容性经过大量项目验证

## 3. CloudBase 关键能力映射

| MVP 需求 | CloudBase 能力 | 实现方式 |
|---|---|---|
| 微信登录 | 内置认证 | `wx.cloud.callFunction` 自动注入 openid |
| 数据 CRUD | 文档数据库 | 小程序端直接读 / 云函数写 |
| 日历实时联动 | 实时数据推送 | 员工端 `db.collection('orders').watch()` 监听订单变更 |
| 轮询兜底 | 文档数据库查询 | watch 断开时降级为 30 秒定时查询 |
| 幂等控制 | 云函数 + 事务 | 云函数内使用 `transaction` 保证原子性 |
| 文件上传 | 云存储 | 头像、协议文件等 |
| 权限控制 | 安全规则 + 云函数 | 敏感操作走云函数校验角色 |
| 微信支付 | 云函数调用微信支付 API | 云函数内完成统一下单和回调验签 |

## 4. 数据模型设计原则

CloudBase 文档数据库为 NoSQL，数据建模遵循以下原则：

| 原则 | 说明 |
|---|---|
| 读多写少的关联数据做**冗余** | 订单中冗余顾客姓名、服务项目名称，减少联查 |
| 写入频繁的数据做**引用** | 营业额分配记录通过 orderId 引用订单 |
| 高频查询字段建**索引** | 订单的 storeId + customerId + payTime 组合索引 |
| 利用 `_openid` 天然鉴权 | 顾客端查询自动按 openid 过滤 |

### 核心集合（Collection）规划

```
stores          - 门店
employees       - 员工
customers       - 顾客（含绑定门店、主美容师）
serviceItems    - 服务项目（三级分类）
orders          - 订单（核心，watch 监听目标）
revenueAllocs   - 营业额分配记录
appointments    - 预约
serviceRecords  - 服务单（到店核销）
bindingApplies  - 门店绑定申请
opLogs          - 操作日志
markets         - 市场
departments     - 部门
```

## 6. 开发步骤

### 步骤 0：业务范围与合规（1 周）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 确认 MVP 范围：登录、浏览、下单、支付（线下）、日历联动 | 飞书/Notion | MVP 范围确认 |
| 注册两个小程序（客户端 + 员工端），开通 CloudBase | 微信公众平台 + 腾讯云控制台 | 两个 AppID + CloudBase 环境 |
| 小程序类目、资质审核材料准备 | 微信公众平台 | 审核材料清单 |

### 步骤 1：工程初始化（2-3 天）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 创建两个小程序项目，开启 TypeScript、CloudBase | 微信开发者工具 | 可运行的空项目骨架 |
| 安装 Vant Weapp，配置构建 npm | npm + 微信开发者工具 | 组件库可用 |
| 初始化 CloudBase 环境，创建数据库集合和索引 | 腾讯云控制台 | 数据库结构就绪 |
| 导入基础数据（门店、员工、服务项目） | 控制台或脚本 | 测试数据就绪 |
| 配置 ESLint + Prettier | 项目配置 | 代码规范统一 |

### 步骤 2：认证与基础架构（3-4 天）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 实现微信登录 + 角色绑定（顾客/店长/美容师） | CloudBase 认证 | 登录闭环 |
| 封装请求层（云函数调用、错误处理） | 小程序端 utils | 统一调用规范 |
| 封装数据库操作层（CRUD + 实时监听） | 小程序端 models | 数据层可复用 |
| 实现门店绑定申请与审批流程 | 云函数 + 数据库 | 门店关联闭环 |

### 步骤 3：交易闭环 - MVP 核心（1-2 周）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 客户端：服务浏览（三级分类）、美容师列表 | 小程序页面 + Vant | 浏览功能完成 |
| 客户端：下单 + 线下付款标记 | 云函数（幂等） | 下单闭环 |
| 员工端：开单 + 营业额分配 | 云函数（事务） | 开单闭环 |
| 员工端：顾客档案 + 日历视图 + 实时监听 | `watch()` 实时推送 | **演示核心完成** |
| 订单状态机：待支付 → 已支付 → 已完成 | 云函数 | 状态流转正确 |

### 步骤 4：服务核销与完善（3-5 天）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 到店服务流程：提交服务单 → 开始服务 → 完成服务 → 扣次 | 云函数（事务 + 幂等） | 核销闭环 |
| 预约管理基础能力 | 数据库 + 页面 | 预约可用 |
| 角色权限控制（店长/美容师数据隔离） | 云函数安全校验 | 权限正确 |
| 异常兜底：轮询降级、重复提交拦截 | 前端 + 云函数 | 健壮性保障 |

### 步骤 5：联调、优化与发布（3-5 天）

| 要做什么 | 工具/平台 | 关键产出 |
|---|---|---|
| 端到端联调：客户端下单 → 员工端日历即时联动 | 两台手机实测 | 演示链路跑通 |
| 分包优化、图片压缩、首屏加载优化 | 微信开发者工具体积分析 | 性能达标 |
| 体验版发布、内部测试 | 微信开发者工具 | 可演示版本 |

## 8. 后续扩展路径

MVP 上线后，根据业务发展逐步扩展：

| 阶段 | 扩展内容 | 技术方案 |
|---|---|---|
| V1.1 | 微信支付接入 | CloudBase 云函数 + 微信支付 API |
| V1.2 | PC 管理后台 | Vue + CloudBase Web SDK（或独立后端） |
| V1.3 | Workfine 数据对接 | 云函数定时触发 + HTTP 请求 |
| V2.0 | 组合套餐、订单转换、退款 | 云函数业务扩展 |
| V2.x | 数据看板、AI 分析 | 云函数聚合查询 + 可视化组件 |

> 若后续 PC 管理后台的查询复杂度超出 NoSQL 承载能力，可引入 CloudBase 的 MySQL 插件或独立后端服务，但 MVP 阶段无需考虑。
