## 二、已拍板的方案

### ✅ 2.1 低价 / 赠送服务的提成保底 —— 提成矩阵加阈值字段

- **业务规则**：划卡提成 = 单价 × 次数 × 比例；为保障美容师手工费，**单价低于 100 按 100 算**（售价 0 或 80，都按 100 × 15% = 15 元）。
- **现状**：只能导出后人工筛选批量改。真正的危害不是工作量，而是**员工认定"看到的提成是错的、反正财务会补"，进而不认真开单**。
- **最终方案**：在**提成矩阵**（已有表）增加一个**阈值字段**，默认 100、**按区域配置**（有的区域 50）；单价 < 阈值按阈值 × 比例，≥ 阈值正常相乘。按**经营类型**分，不分品项、不分门店，**仅限自销**。
- **被否决**：把 15 元加到手工费 + 下调提成比例（15%→14%）——夜航星现场画图证明两者数学等价（两条线在 100 元处重合），但**等于改工资标准**，没法对几百名员工解释，员工会算"消耗越多差距越大"，张凯否决。
- 备选参考：邵冬的"每日审工资单、月底取已审数据"——最笨但最直接。

## 三、进销存：确认的业务口径与待改项

**层级**：供应链（品项公司/总部）→ 市场（区域）→ 门店；另有市场间调货、退货。
**铁律**：**价格在每个层级都会变一次**，历史单据必须保留当时价格（快照）。

### 已确认口径

| 环节 | 口径 |
|------|------|
| 门店报货 | 日期固定 5/15/25 号（加批次也全公司统一）；支持草稿；**金额、供货商不给门店看** |
| 市场汇总 | 按日期提取本市场全部门店报货；填采购数量（不填=不采购）；**单价优惠不可手填**，由「报货福利」按商品编号+市场+日期自动提取（带阶梯）；提交后锁定 |
| 汇总市场报货单 | 供应链汇总**全国各区域**同日期报货，唯一用途是**会计看每个市场要收多少钱** |
| 采购订单 | = 市场汇总 **+** 品项公司需求；**只按日期汇总**报货单；多一个「采购数量」（自有库存够可不采） |
| 采购入库 | 可分批录入；批号自动生成，每次流转算一批；**可填优惠**（厂家活动使实际进价低于标准价，不改商品属性） |
| 发货（物流中心配货单） | 以区域为单位；**引用市场原始报货单**（非汇总单）；从库存按批号逐行选；一行不能对应多批号，不足需新建表单分多次发 |
| 赠送 | 发货时自己新增行、价格 0；**数量不对等**（报 10 发 12）；**不平摊单价**；「是否赠送」属性从采购入库起跟着批号走，**独立批号** |
| 市场入库 | 走流程非新建；引用配货单，数量金额**不可改**；同时关联市场报货单以追溯累计入库 |
| 市场配门店 | **门店可不提需求由市场直接发货**（且这是主流）；默认价 = 商品的门店进货价；主管可填优惠；黄色字段显示该批号市场实际进货成本供参考 |
| 门店入库 | 引用配货单，只见本店单据；正常不可改数量 |
| 门店出库 | 顾客领走：选顾客→选销售单（仅剩余未取的）→ **出库金额 = 该商品顾客实际售价**，用于店长提成（预存款转收入=消耗）；**报损也走正常出库** |
| 盘点 | 门店每月≥3 次、市场 1~2 次；盘盈按标准价；口径"**可以多不能少，少了罚钱**"；找不出原因就纠正进去 |
| 货款结算 | 按市场提整月；**以市场发货（配货）时间为准，不管门店是否及时入库**（内部规定）；优惠来自配货时填的字段 |
| 库存转换 | **仅供应链可做**；选现有批号+数量+目标商品，**生成新批号**；价格自填但**上下必须对等**；支持多对多与拆分 |
| 市场/门店自建商品 | 区域可自行建档采购，供应链不管；无流程直接增库存；**不能做转换** |
| 市场间调货 | 先出后入；跳标准价；**可减价不可加价**（可优惠到 0）；市场间独立结算 |

### ⚠️ 关键纠正：采购订单不按供应商拆分

凤御按**批次**采购（9/5、9/10、9/15、9/20、9/25、9/30 固定），一批次里所有供应商并成一张——会计只需知道这批对外采购总额。系统当前按供应商区分，20 个供应商要建 20 张单，**不成立**。

## 四、权限架构：交叉权限需要换模型

**两类诉求**：

- **推广部**：市场 → 推广部 → 分组 → 推广员；主管看下属卖卡数与对应顾客，市场老总看各市场卡数与一次/二次业绩（顾客生命周期）；
- **品项公司**：属供应链不属市场；品项老师**只看每家店"剩余我这个品项的顾客"**，不受门店/市场限制，受商品的品项字段限制。

**技术判定（夜航星）**：这是**交叉权限**。需从 **RBAC → RBAC + 资源（domain）**：把市场/门店变成资源、品项也变成资源，推广部/品项层级作为另一侧去匹配。灵楔用 Casbin 表达式可支持多权限模型切换，本项目做项目没这么精细，切换会费劲。

**风险**：权限 bug **漏一条就挂**；测试环境不一定能暴露；最耗时的是构建不同角色测不同场景（排列组合多，用 AI 测也得人工看结果）；之前的特殊处理（技能那块）要一起更新，极易漏；线上不允许宕机一两天。

**结论**：排期在数据中心和进销存之后。期间用**导出明细按维度拆分后发给对应的人**顶着，夜航星提议"这个流程可以让 AI 干——写个固定的 skill"。

**简化路径**：品项若不细分（全给、自己筛选），**现有权限就够用**，卡点只在手机端没有疗程卡页面（品项老师要看「剩余疗程卡」+「顾客档案」）。

## 五、数据中心外部端改造（7 个页面）

**前提：没有新增字段**，只是排版与聚合方式不同（经营类型、一级/二级品项商品里都有）。

1. 门店 × 经营类型 / 一二级品项 业绩消耗汇总
2. 顾客清单 × 日历（当日到店绿勾 + 当日消费金额，右滑；合计本期到店次数与消费）——**目前店长拿 A4 纸画**
3. 顾客 × 品项 交叉表（有剩余卡打勾、已服务完备注、没买过空白）——品项老师据此开发与跟进复购
4. 保有会员 / 被经营顾客 / 销售业绩 / 客流客单（目前各区域财务人工做）
5. **员工目标填报 + 完成情况**（美容师/门店/市场三维度分页）— 新板块
6. **经营周期配置表**（如每月 26 至次月 25，也支持自然月；周起止可自定义，生成本地日历）— 新板块
7. 员工提成明细（员工 × 每天，含销售与服务提成，可下钻）

**要点**：

- **日期筛选只能是单个日期**：底下有"当月/当年"类字段，选跨月区间就无法定义"当月"——这正是员工端"只有一个日期没有区间"的成因，非 bug；
- **目标各填各的**：员工合计 ≠ 门店目标；且**目标必须与日报同源**；
- **经营周期的连带影响**：有了它就不用为纠正日期改单据，但**业绩归属日期功能要保留**（应对宕机补单等突发，邵冬坚持）；**分析师也受影响**——需多调一次经营周期接口确定时间范围；
- **工作量**：聚合页面 + 目标填报 + 经营周期 ≈ **额外一个月**；不用和原型一模一样，但"一模一样还快一点"。

**未决**：品牌与市场字段是否拆分。邵冬主张现在就加品牌字段（娇莉芙、[医大师?] 独立于美丫丫，现在市场与品牌柔和在一起，"合在一起容易、分开来难"）；张凯认为改市场名即可。

## 七、AI 培训 / 学习中心

张凯已用 AI 画出完整原型，**已在公司会议上展示过，万总当场表示"这个东西很重要"**（现状是几百人拉到会场讲一天，既无留痕也无数据分析）。

**结构**：

- 员工端：课程（分类/视频/课时）、**AI 对练**（管理员建虚拟场景，员工也可自建——填性别/画像/性格/收入；卡壳时灯泡提示 AI 教怎么答）、我的（打卡、对练次数、平均分、学习时长、证书、错题本）、考试中心；
- 对练评分：**话术 / 服务态度 / 专业知识 / 应变 / 销售技巧** 五维雷达 + 优点与改进点；
- 管理层：本市场/本店员工排行 → 每人每课程学习情况与完成率 → 也可按课程反查；
- 品牌总部：培训覆盖率 → 市场 → 门店 → 员工。

**交付形态倾向移动端网页**（非小程序）：独立部署给独立链接，放公众号自定义菜单或企业微信跳转。理由——开发量少、不同产品可统一、小程序要不停提交代码审核。课程/考试/对练各行业通用，"改个名字就是了"。

**技术方判断**：功能好做，但接触不到这类需求（客户不会把培训排第一，排前面的是引流等跟销售有关的）；评分调教有对应学科与更新知识可借鉴（不直接用书本）；考试设计有**信度**（同人不同时分数稳定）与**效度**（考核与技能匹配）两个指标。

**资料基础**：凤御商学院已有整套话术与项目培训流程（有存档），只是没形成可在线查看的库。

**邵冬的商业化提议（张凯未接）**：报高价 + 张凯帮推销则分成；另设"使用频次达标退 5 万"条款逼老板推动员工真用起来。张凯回应：拉赞助得先有产品，且技术方至今没给一份"能做什么 + 报价"的材料。

## 八、需求变动的代价（夜航星说明）

- 需求一直变，改一处有副作用，每次都要做**一致性检查**；
- **归属日期**改动很大——所有跟时间相关的都变了；**家居产品**加进转换单后，转换和退款都跟着变；
- **不敢重构**（会影响线上），只能打补丁——"**补丁就是补丁，不能作为栋梁；打补丁本身很脆，你老改它就更脆了**"；
- **现在改需求，测的时间比写的久**。

**两套系统的根本差异**：WorkFine 是表单（无中间过程，状态在人脑里过，付成功就保存、失败就删单）；美丫丫是分节点的状态机（开单→转换/退款，连付款都有多个只存在几分钟的中间状态，也必须保证不出问题）。

- **SaaS 化**：张凯规划多品牌 + 加盟店（数据隔离、可换名、规则可自定义，如会员等级门槛）。夜航星：当前系统逻辑不同不能迁移，要对外卖得 copy 一份。**灵楔**——下月先出命令行并优先开发**灵楔美业**（整合通用业务、顺便测产品），12 月出 SaaS Beta。张凯："以后我们卖不如直接卖灵楔，自定义更强，但我可以打我的招牌"；
- **为什么不用美滴滴**（张凯给万总的理由）：①数据在别人手上，数据即资产；②业务逻辑定死，门店模式一变就只能乱录，导致衍生数据与分析全错；
- **千宝[?]** 报价放弃：单次从几分涨到几毛，一年十几万；
- **降本成果**：南昌凤御 18 家店原每店 1 助理、月均 5000（未含社保）≈ 9 万/月、**超 100 万/年**，现只需 3 人，省约 15 人；九江留 2 人；自贡难砍（3 年以上老员工，N+1 + 今年才开始交社保）。部分店长宁愿自掏工资独享助理。昭通本月培训、下月启用，吉安也将启用；
- **工资核对的机制风险**（贯穿全场）：美容师实时能看到提成，若与实发不一致，就会形成"订单错了没关系、财务会补"的心态，系统数据质量随之崩塌。张凯的立场是"**美丫丫上显示 1900 就发 1900**"。
