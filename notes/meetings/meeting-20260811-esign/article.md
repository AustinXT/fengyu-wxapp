## 一、讨论背景与目标

美丫丫希望把电子签章能力接入现有业务系统，解决三类问题：

1. 连锁门店存在约 50 个经营主体，劳动合同、股东协议及其他文件需要按实际主体签署，单一企业账号难以覆盖。
2. 顾客购买套餐、进行服务核销、退款或转换项目时，目前系统虽有业务台账，但缺少顾客本人确认所形成的完整证据链。
3. 公司制度、通知函等内部文件下发后，门店可能以“未收到、未阅读”为由拒绝执行，需要保留送达、阅读或确认记录。

本次会议的核心不是立即确定采购，而是确认 e签宝的产品能力、接入方式、签署动作、费用构成及业务流程能否闭环，再决定是否进入测试。

## 二、e签宝产品与多主体能力

### 1. 产品形态

e签宝代表介绍，产品可通过 SaaS 网页端、手机 App、支付宝小程序和微信小程序使用，各端消息互通。网页登录支持微信、钉钉、企业微信、飞书、短信验证码及密码等方式。

发起签署主要有两种方式：

- **上传文件**：适用于已在业务系统或本地制作好的非标准合同，上传后配置单方、双方或多方签字、盖章位置。
- **选择模板**：适用于劳动合同、采购合同等标准文件，提前在后台配置模板后重复发起。

### 2. 关联子企业

针对集团和连锁企业，e签宝提供“关联子企业”能力：总部以主企业身份购买产品后，可将功能、套餐、API 能力和部分权限共享给下属企业，关联对象可包括个体工商户。

各子企业的印章可以授权总部统一管理。子企业人员需要用印时，可先经过总部指定负责人审批，再调用相应印章。该能力与美丫丫多门店、多经营主体的情况基本匹配，但可关联主体数量及扩展包费用仍需书面确认。

## 三、拟覆盖的签署场景

会议识别出以下场景：

| 场景 | 主要目的 | 讨论中的优先级/判断 |
|------|----------|--------------------|
| 顾客购买套餐或商品 | 顾客确认交易内容、金额和协议 | 对外场景，需重点保证合规 |
| 服务完成与疗程卡核销 | 证明顾客已接受服务并同意扣减次数 | 当前最直接的证据痛点，也是最大调用量来源 |
| 退款、取消、转换单 | 记录原合同变化及顾客确认 | 尚未形成完整规则，需要逐类设计 |
| 门店经营主体更换 | 明确服务承接主体变化 | 原主体注销、新主体设立时原则上需重新取得顾客确认 |
| 劳动合同 | 员工与实际用工主体签约 | 需要合规，但相较顾客消费不是最高频场景 |
| 股东协议 | 固化内部权利义务 | 业务方认为是明显痛点 |
| 公司制度、通知函 | 证明文件已送达、已读或已确认 | 偏内部场景，可评估较轻量的确认流程 |

### 当前痛点

现有服务流程是：美容师开始服务，服务完成后由顾客确认，系统再扣减疗程卡次数。虽然系统能够导出核销明细，但会议认为，这类内部台账不等同于具备完整签署证据链的电子文件。一旦顾客否认接受过服务，企业处理投诉或举证仍然困难。

业务方强调，如果决定建设电子签能力，就应覆盖购买、履约、转换、退款等关键变化，避免只完成其中一段，仍然无法闭合证据链。

## 四、API 与 SDK 两种接入思路

### 1. 打包式 API/页面跳转方案

一种方式是调用供应商的标准能力并跳转到其签署页面，由供应商完成实名、意愿认证和签署等流程。该方案接入相对直接，页面和流程由供应商承接，但单次综合成本较高。

会议初步确认，供应商可提供实名、合同文件签署、印章调用、验签等接口。具体开放范围、接口文档和是否完全满足美丫丫流程，需在拿到文档后由技术方继续评估。

### 2. SDK 组件化方案

另一种方式是接入 SDK，由美丫丫开发业务页面，并按实际调用的能力分别计费，例如实名、签署、短信或刷脸认证。供应商提供身份认证和签署底层能力，合同及相关业务数据主要由美丫丫侧管理。

SDK 方案预计成本较低，但会增加以下工作：

- 美丫丫自行设计并开发签署页面和业务流程；
- 明确合同原件、签署结果、存储链接及长期归档责任；
- 接入验签接口，保证多年后仍能验证文件；
- 处理短信、刷脸等不同意愿认证通道；
- 为失败、取消、超时、退款、主体变更等情况补齐状态机。

### 3. 实名认证与意愿认证不是同一动作

会议中供应商将两类认证区分开来：

- **实名认证**：证明签署人身份，通常同一顾客首次进入平台时完成一次。
- **意愿认证**：证明顾客对某次具体签署作出了真实确认，可能通过短信验证码或刷脸完成，通常会随签署事件发生。

因此，首次实名后并不意味着以后所有合同都可以完全无感签署。顾客仍需看到待签文件并表达签署意愿。

## 五、调用量与口头报价

### 1. 业务量估算

现场以“每店每天约 15 次需要签署或确认的动作、约 50 家门店”进行粗算：

`15 × 50 × 365 = 273,750 次/年`

该数字主要考虑高频服务核销。若再纳入购买、退款、转换单、主体变更等场景，全年可能达到 30 万至 35 万次。实名认证的调用量相对较少，因为同一顾客原则上只需完成一次。

### 2. SaaS 与多主体套餐

会议中先后出现多组口头价格：

| 项目 | 现场口头信息 | 状态 |
|------|--------------|------|
| 专业版 | 曾提到 9,800 元/年；供应商又表示可申请至 7,800 元/年，官网价被口述为 16,800 元 | 待书面报价统一 |
| 约 50 个主体扩展包 | 曾提到 14,000 元/年；后表示可申请至 8,000 元/年 | 待确认主体数量及计费边界 |
| 优惠后合计 | 约 15,800 元/年 | 仅为现场口头方案 |

### 3. 高频顾客签署

打包式方案最初被口头估算为每个流程约 0.4—0.5 元，若按 20 万次计算，年度费用约 8 万—10 万元，业务方认为明显超出预期。

SDK 方案的描述在现场有数次修正：一度表达为每次流程低于 0.1—0.2 元，随后又提到签署能力公开价约 0.05—0.06 元/次，并尝试按约 0.04 元/次申请大客户价格。按 27.375 万次、0.04 元/次粗算，仅签署调用约 1.095 万元/年，但这不一定包含实名、短信/刷脸、存储、证据报告及其他费用。

会议后业务方按自身理解粗估：基础 SDK 使用一年约 2 万余元，叠加主体变更及其他场景后可能达到约 5 万元。该估算不是供应商正式报价。

### 4. 出证费用

发生诉讼或对证据链有额外要求时，可向供应商申请证据报告。现场口头提到约 100 元/份，按需购买。合同原件本身可保留签章和签名，但是否需要额外报告取决于争议处理或司法机构的要求。

### 5. 报价中必须拆清的项目

下一版报价至少应分别列出：

- SaaS 专业版费用；
- 关联企业/主体扩展包费用及数量上限；
- API 或 SDK 的一次性接入、技术服务或启动费用；
- 实名认证单价；
- 短信意愿认证与刷脸意愿认证单价；
- 单次签署、验签和文件存储费用；
- 证据报告及加急服务费用；
- 测试环境、生产环境和售后支持边界。

## 六、关键合规与流程问题

### 1. “完全无感签署”不可作为设计目标

业务方希望尽量减少顾客操作，尤其不希望每次服务都要求刷脸。会议形成的基本认识是：如果需要形成具备法律意义的签署，不能只靠后台自动勾选或默认为同意，必须保留顾客看到文件并主动确认的过程。

可优化的是交互成本，例如在服务完成时集中展示需要确认的内容、提供短信和刷脸两种通道，但不能省略真实意愿表达。

### 2. 门店主体注销后由新主体承接

部分门店可能保持地址、员工和服务不变，但原个体工商户注销，另行设立没有法律承继关系的新主体。会议讨论认为：

- 原合同仍然记录顾客与原主体的关系，不能直接把合同抬头一键替换成新主体；
- 新主体继续提供服务时，应取得顾客对服务承接或合同变更的确认；
- 可以考虑在顾客下一次到店服务时，先展示主体变更/服务转移通知，再与本次服务确认一并完成；
- 仅有平台公告或“已读”状态是否足够，现场判断偏否定，仍需法务进一步确认。

业务方担忧主动提示“换主体”会引起顾客疑虑，这是经营沟通问题，不是单靠技术可以消除的问题。

### 3. 退款、取消与转换单

如果订单取消、部分退款、服务取消或套餐 A 转换为套餐 B，原签署文件应如何处理，会议没有得出最终方案。转换单也属于订单变化，可能涉及补款、等价替换或部分消耗，调用量会因此增加。

后续需要为每类单据确定：

- 原合同是否继续有效；
- 是否生成解除协议、补充协议或新的确认单；
- 哪些动作必须由顾客再次确认；
- 已完成服务和未完成服务如何拆分；
- 退款、转换和签署文件之间如何相互关联。

### 4. 成本与风险要一起评估

业务方表示，当前真正进入诉讼的案件不多，但顾客投诉、否认服务、制度无法落地等零散问题经常发生。最终是否采购，应比较两类成本：电子签章的年度显性支出，以及纠纷处理、投诉损失、员工时间和管理摩擦等隐性成本。

## 七、电子签章部分的阶段结论

本次会议没有作出采购或技术选型决定，只形成以下方向：

1. e签宝具备多主体、模板、API/SDK、实名、意愿认证、验签等基础能力，原则上可进入进一步评估。
2. 高频顾客场景应优先比较 SDK 方案；SaaS 平台可用于劳动合同、股东协议或低频内部文件，但是否需要两套形态要看最终报价。
3. 服务核销是当前最大量、最明确的证据痛点，购买、退款、转换和主体更换必须一并纳入流程清单。
4. 完全无感且具备法律效力的自动签署不可行，交互设计需在合规与顾客体验之间平衡。
5. 供应商需提供书面方案、完整报价和接口资料，技术方再通过测试环境验证流程。
6. 业务方会横向比较其他电子签服务商及较官方的 CA 服务方案，会议中举例提到浙江 CA。

## 八、供应商离场后的库存讨论

### 1. 库存试运行步骤

会议后半段转入库存模块。初步测试顺序为：

1. 先导入并配置产品/物料信息及价格表；
2. 录入各测试门店的期初库存；
3. 开始执行入库、出库、提货等业务流转；
4. 选择测试门店，核对实际库存与系统库存是否一致；
5. 对账稳定后再扩大测试范围并全面铺开。

### 2. 顾客已购单品缺少集中展示

当前顾客档案可以看到疗程卡和消费记录，但不能直观看到顾客购买过哪些单品、购买数量、已提取数量和剩余数量。例如顾客购买 10 支产品、中途提走若干支后，员工无法在档案中快速确认剩余可提数量。

讨论倾向于在顾客档案中增加与疗程卡类似的“已购商品/提货记录”区域，至少展示：

- 商品/SKU；
- 购买数量；
- 已提数量；
- 剩余数量；
- 对应订单；
- 提货明细。

当前提货与库存尚未完全关联。早上提出的两个 SKU 也需要先完成关联；库存数据录入并打通后，顾客提货才能正确触发出库。

### 尚未确认
