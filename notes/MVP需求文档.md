# 凤御美业小程序 MVP 需求文档

> **MVP 目标**：完成会议演示所需的板块一（顾客端）和板块二（员工端），核心演示 **"顾客下单 → 员工端日历即时联动"** 的完整链路。
>
> **MVP 定位**：会议演示版，面向店长级别以上管理层及老总，需具备完整的下单→联动链路，界面可用、流程可跑通。

---

## 一、演示核心链路

以下为会议现场需跑通的完整流程：

**场景 A：客户端自助下单**

| 步骤 | 端口 | 操作 |
|------|------|------|
| 1 | 客户端 | 选择一个服务项目 |
| 2 | 客户端 | 分配美容师 |
| 3 | 客户端 | 提交1万元订单，选择"线下付款" |
| 4 | 员工端 | 店长确认线下收款 |
| 5 | 员工端 | 进入顾客档案 → 日历视图 |
| 6 | 员工端 | 日历上实时出现标记：该顾客今日消费1万元 |

**场景 B：员工端开单（扫码收款）**

| 步骤 | 端口 | 操作 |
|------|------|------|
| 1 | 员工端 | 店长选择顾客，添加服务项目，完成营业额分配 |
| 2 | 员工端 | 系统生成订单二维码，展示在屏幕上 |
| 3 | 客户端 | 客户微信扫码，打开客户端小程序，看到订单详情 |
| 4 | 客户端 | 客户确认付款（微信支付或线下付款） |
| 5 | 员工端 | 若线下付款则店长确认收款；若微信支付则自动到账 |
| 6 | 员工端 | 进入顾客档案 → 日历视图，日历实时出现消费标记 |

**核心要求**：订单进入`已支付`后日历立刻有反馈，体现即时联动效果。

### 两种下单方式

系统支持两种下单方式，均生成等价订单并触发员工端日历联动：

| 方式 | 操作端 | 操作人 | 营业额分配 | 使用场景 |
|------|--------|--------|------------|----------|
| 客户端下单 | 客户端 | 顾客自助 | 下单时不分配，店长后续在 PC 端分配 | 顾客自主消费、线上购买 |
| 员工端开单 | 员工端 | 店长代客 | 开单时即完成分配 | 到店消费、店长推荐项目 |

- 客户端下单时选择美容师**非必须**；若指定则该美容师独享销售提成
- 员工端开单仅限**店长（门店经理）**操作

#### 员工端开单完整流程

员工端开单并非在员工端直接完成支付，而是通过二维码引导客户在客户端完成付款：

```
店长开单 → 生成订单二维码 → 客户微信扫码 → 打开客户端小程序 → 自动生成相同订单 → 客户确认付款 → 流程完成
```

| 步骤 | 端口 | 操作 | 说明 |
|------|------|------|------|
| 1 | 员工端 | 店长选择顾客、添加项目、完成营业额分配 | 创建待支付的订单记录 |
| 2 | 员工端 | 系统生成订单二维码 | 二维码包含订单ID，指向客户端小程序 |
| 3 | 客户端 | 客户微信扫码，打开客户端小程序 | 小程序通过场景值解析订单ID |
| 4 | 客户端 | 小程序自动加载订单信息，展示订单详情 | 客户看到与员工端开单一致的项目和金额 |
| 5 | 客户端 | 客户确认并选择支付方式（微信支付/线下付款） | 客户主动确认付款意愿 |
| 6 | 双端 | 支付完成，订单进入`已支付`，触发日历联动 | 线下付款需店长额外确认收款 |

**关键设计要点**：
- 二维码为小程序码或小程序链接二维码，扫码后直接跳转客户端小程序的订单确认页
- 订单在员工端开单时即写入数据库（状态为`待支付`），客户扫码后无需重复创建
- 客户扫码后看到的是同一笔订单，非新建订单
- 若客户未扫码或未付款，订单保持`待支付`状态，可设定超时自动关闭

## 二、客户端（C端）功能范围

### 2.1 服务浏览

- 展示门店的美容服务和产品列表
- 商品分类三级结构：
  - **一级**：服务、产品
  - **二级**：品项类别（蜜语生玑、科颜美、诺千金、缦之羽、中华神灸、圣源养心、安吉丽美颜之爱等）
  - **三级**：具体项目名称
- 每个项目展示：名称、价格、描述信息
- 品项的"生美"与"非生美"区分
  - **生美**（生活美容）：基础护理类项目，业绩归属美容部美容师
  - **非生美**：科技美容（科颜美）、医疗美容（诺千金）、养生（圣源养心）等专项类目，业绩归属对应专项部门
  - 此区分影响**营业额分配时的部门选择**和**后台数据统计维度**

> **MVP 简化**：组合套餐（促销方案）暂不纳入，一级分类中暂不展示"促销方案"入口。

### 2.2 门店选择

- 首次使用时从门店列表中选择绑定默认门店
- 绑定后默认显示所选门店的服务和产品
- 门店绑定需本店店长在员工端同意确认
- 绑定申请状态需明确为：`待审批` / `已通过` / `已拒绝`
- 同一顾客同一时刻仅允许存在一条`待审批`绑定申请，避免重复提交
- `待审批`期间允许浏览门店信息，不允许创建订单；`已拒绝`后可重新发起申请

> **MVP 简化**：更换门店功能暂缓，MVP 只支持首次绑定。

### 2.3 美容师选择

- 浏览门店美容师列表
- 查看美容师的预约状态（空闲/忙碌）
- 下单时可选择指定美容师（**非必须**）
  - 若指定 → 销售提成归该美容师
  - 若未指定 → 店长后续在 PC 端分配

### 2.4 下单与支付

- 选择服务项目后发起下单
- 支付方式支持：
  - **线下付款**（MVP 演示重点，采用双阶段：顾客提交 → 店长确认收款）
  - 微信支付（小程序内支付）
- 下单时需勾选消费协议（协议具体内容待甲方提供，MVP 可使用占位文本）
- 订单进入`已支付`后，订单信息实时推送至员工端
- 订单状态最小集：`待支付` / `待确认收款` / `已支付` / `支付失败` / `已关闭`
- **线下付款（MVP 口径）**：顾客提交后记为`待确认收款`，店长确认后置为`已支付`
- 支付成功触发条件统一为`订单进入已支付`，而不是“仅创建订单成功”
- 需实现提交防重：同一订单请求仅允许创建一次（前端防连点 + 后端幂等校验）

> **MVP 简化**：充值卡金抵扣、优惠券、待转金等高级支付功能暂缓。

### 2.5 订单管理

- 查看订单列表和订单详情
- 订单信息包含：订单状态、服务内容、金额、美容师、下单时间
- 查看已购买服务的剩余次数

> **MVP 简化**：订单转换、退款功能暂缓。

### 2.6 到店服务流程

- 到店后提交服务单（触发疗程卡次数核销）
- 查看服务进行状态（待服务/服务中/已完成）
- 仅疗程卡类项目进入“到店服务”流程；家居产品支付完成后直接为已完成，不走核销
- 服务状态流转仅允许单向前进，禁止逆向修改
- 服务完成时才扣减疗程卡次数；需保证并发下不出现“重复扣次”

## 三、员工端（B端）功能范围

### 3.1 开单（核心功能）

- **权限**：仅店长（门店经理）可开单
- 开单流程：选择顾客 → 添加项目（疗程卡/家居产品）→ 营业额分配 → 生成订单二维码 → 客户扫码确认付款
- 员工端开单后**生成二维码**，客户扫码后在客户端小程序完成支付
- 员工端开单时订单即写入数据库（状态`待支付`），客户扫码后加载同一笔订单进行付款
- 客户在客户端可选择微信支付或线下付款
- 线下付款订单需由店长在员工端执行"确认收款"后才进入`已支付`
- 员工端开单页需展示二维码状态：待扫码 / 已扫码待付款 / 已付款
- 门店未配置店长时，MVP 阶段不开放"授权员工开单"，前端直接提示"请先配置门店店长"

> **MVP 简化**：组合套餐开单暂缓；优惠金额、是否赠送功能暂为默认值（开关在 Web 端控制，MVP 可硬编码）。

### 3.2 营业额分配（核心功能）

开单完成后，店长进行营业额分配：

#### 基本规则
- 先选择部门，再选择该部门下可分配业绩的员工
- 可分配业绩的员工由"是否可分配业绩"字段控制

#### 同部门分配
- 多名美容师参与时，分配总额 ≤ 实收金额
- 店长可选择分配比例（3:7、4:6、5:5、2:8 等）

#### 跨部门分配
- 美容部为基础服务部门
- 跨部门时各部门可各按实收金额分配（总额可达实收 2 倍）
- 例：推广部引流 + 美容部服务 → 各分配 10000 元

#### 默认跳出人员
- 顾客档案绑定的主美容师
- 顾客预约的美容师

> **MVP 简化**：仅支持销售单的营业额分配；转换单、回款单、退款单的分配暂缓。充值卡金的营业额分配暂缓。

### 3.3 顾客档案与日历视图（演示重点）

- **顾客档案**：展示顾客基本信息、消费记录、绑定门店
- **日历视图**：
  - 按日展示顾客消费记录
  - 每日标记消费金额
  - **实时更新**：顾客订单进入`已支付`后日历立即显示消费标记
  - 支持按月浏览
  - 同一顾客同一天多笔订单需按日汇总金额，并可展开查看明细订单
  - 日历入账口径按`已支付时间`统计，`待支付/待确认收款/支付失败/已关闭`订单不得入账

> 这是会议演示的**核心亮点**，需确保下单→日历标记的实时性和视觉效果。

### 3.4 预约管理

- 查看顾客预约信息
- 确认开始服务 / 服务完成
- 消息提醒功能

### 3.5 门店绑定审批

- 顾客在客户端发起门店绑定申请后，店长在员工端收到申请通知
- 店长可同意或拒绝绑定申请
- 同意后顾客自动归属该门店，可浏览该门店服务并下单
- 拒绝后需记录拒绝原因（至少保留一条文本备注）并回传客户端可见
- 审批动作需写入操作日志（审批人、审批时间、审批结果）

### 3.6 数据访问权限

- 按角色分配不同数据访问范围：
  - 店长：本店所有数据
  - 美容师：本人相关顾客数据
- 技师无法看到客户真实电话号码
- 项目部门人员按品项类别查看对应顾客档案

> **MVP 简化**：权限体系实现基本角色区分（店长/美容师），细粒度权限配置暂缓。

## 四、后端服务需求

### 4.1 数据模型

| 实体 | 关键字段 |
|------|----------|
| 门店 | 名称、所属市场、地址、状态 |
| 员工 | 姓名、职位、所属门店、所属部门、是否可分配业绩 |
| 顾客 | 姓名、手机号、绑定门店、主美容师 |
| 服务项目 | 名称、分类（三级）、价格、生美/非生美标记 |
| 订单 | 订单号、顾客、项目、金额、支付方式、支付状态、下单端、下单人、美容师、支付时间、线下确认人、线下确认时间 |
| 营业额分配 | 订单ID、员工、部门、分配金额 |
| 预约 | 顾客、美容师、时间、状态 |
| 服务单 | 订单ID、顾客、服务人、开始时间、完成时间、状态、扣减次数 |
| 门店绑定申请 | 顾客ID、申请门店、状态（待审批/已通过/已拒绝）、审批人、审批时间、拒绝原因 |
| 操作日志 | 业务类型、业务ID、操作人、操作动作、时间、变更前后值 |
| 市场 | 名称、编号 |
| 部门 | 名称、所属市场/门店、类型 |

### 4.2 核心接口

| 接口 | 说明 |
|------|------|
| 用户认证 | 微信小程序登录、手机号绑定 |
| 门店 | 门店列表、门店详情、门店绑定 |
| 服务浏览 | 分类列表、项目列表、项目详情 |
| 美容师 | 列表、预约状态查询 |
| 下单 | 客户端下单、员工端开单、二维码生成 |
| 支付 | 微信支付、线下付款提交、店长确认线下收款 |
| 订单 | 订单列表、订单详情、订单状态更新 |
| 营业额分配 | 部门查询、可分配员工查询、分配提交 |
| 顾客档案 | 顾客信息、消费记录、日历数据 |
| 预约 | 创建预约、预约状态更新 |
| 服务单 | 创建服务单、开始服务、完成服务、核销次数 |
| 门店绑定审批 | 绑定申请列表、同意/拒绝审批 |
| 幂等控制 | 下单、支付回调、服务完成接口幂等校验 |
| 实时推送 | 订单进入已支付后即时通知员工端 |

### 4.3 实时通信

- 订单进入`已支付`后，员工端需**即时感知**并更新日历视图
- 技术方案：WebSocket 或小程序消息订阅
- 兜底机制：WebSocket 断开时，员工端每 30 秒轮询一次顾客日历数据，恢复连接后回到实时推送

### 4.4 Workfine 数据对接（MVP 必须）

MVP 阶段采用**双数据库架构**，Workfine 的 SQL Server 数据库作为小程序后端的业务数据库之一，云函数直连读写：

```
小程序 → CloudBase 云函数 → 多数据库后端
                              ├── CloudBase DB（小程序专属数据）
                              └── Workfine SQL Server DB（直连读写）
```

#### 数据库分工

| 数据 | 存储位置 | 读/写 | 说明 |
|------|---------|-------|------|
| 员工（姓名、职位、门店、部门、是否可分配业绩） | Workfine DB | 读 | 业务主数据，由甲方在 Workfine 设计端维护 |
| 服务项目/产品（名称、价格、分类） | Workfine DB | 读 | 含"原价"即开单价格 |
| 组织架构（市场、部门、门店） | Workfine DB | 读 | 人事架构以 Workfine 为准 |
| 销售单/订单 | Workfine DB | 写 | 写入 Workfine 已有的销售单表单 |
| 营业额分配记录 | Workfine DB | 写 | 写入 Workfine 已有表单 |
| 服务核销记录 | Workfine DB | 写 | 疗程卡扣次写入 Workfine |
| 微信用户（openid、session、手机号绑定） | CloudBase DB | 读写 | 小程序认证专属，Workfine 无此概念 |
| 实时推送状态 | CloudBase DB | 读写 | WebSocket 连接与消息队列 |
| 门店绑定申请 | CloudBase DB | 读写 | 小程序专属审批流程 |
| 操作日志 | CloudBase DB | 写 | 小程序侧操作留痕 |

#### Workfine 对接要点

- **连接方式**：云函数通过 `mssql`（node-mssql）驱动直连 Workfine 的 SQL Server 数据库
- **服务器地址**：`111.229.31.128`（需确认端口与数据库凭据）
- **读取**：直接 SELECT 查询员工表、产品表、组织架构表
- **写入**：订单进入`已支付`后，通过 INSERT 写入 Workfine 对应的销售单表，需严格遵循 Workfine 已有的表结构和字段约束
- **前置条件**：需甲方提供 Workfine 数据库的表结构文档或直接开放查询权限，以便确认字段映射关系

## 五、组织架构与角色

### 5.1 人事架构

```
品牌总部
└── 市场（如南商市场）
    ├── 部门（美容部、推广部等）→ 直属于市场
    └── 门店
        ├── 门店经理（店长）→ 直属美容部
        └── 美容师
```

### 5.2 MVP 涉及角色

| 角色 | 端口 | 核心能力 |
|------|------|----------|
| 顾客 | 客户端 | 浏览服务、下单支付、查看订单 |
| 店长（门店经理） | 员工端 | 开单、营业额分配、查看顾客档案/日历、预约管理 |
| 美容师 | 员工端 | 查看预约、确认服务开始/完成、查看相关顾客信息 |

## 七、关键业务规则（MVP 需遵循）

1. **只有店长（门店经理）可开单**，普通美容师无开单权限
2. **营业额分配**：同部门总额 ≤ 实收；跨部门各按实收分配
3. **门店经理直属美容部**，其他部门从门店所属市场查询
4. **美容师选择非必须**：顾客下单时可不指定美容师
5. **技师不可见客户真实电话**
6. **门店绑定需店长确认**
7. **日历入账口径**：仅`已支付`订单计入当日消费
8. **幂等要求**：下单、支付回调、服务完成三类接口必须幂等
9. **线下付款口径（仅 MVP）**：顾客端选择线下付款先进入`待确认收款`，店长确认后才计为`已支付`

### 疗程卡生命周期（MVP 范围）

疗程卡是核心商品形态，MVP 需实现其基本生命周期：

```
购买 → 到店核销（扣次） → 次数归零（完成）
```

| 阶段 | 说明 |
|------|------|
| **购买** | 通过客户端下单或员工端开单购买疗程卡，订单记录总次数、总金额、单次价格 |
| **到店核销** | 顾客到店提交服务单 → 技师确认开始服务 → 确认服务完成 → 剩余次数减 1 |
| **次数归零** | 所有次数消耗完毕，疗程卡状态变为已完成 |
| **剩余次数查询** | 客户端订单详情中展示剩余次数；员工端顾客档案中可见 |

> **MVP 简化**：分期回款（分次付款）、转换单、退款单暂缓。MVP 阶段疗程卡为一次性全额支付。

## 九、状态机与异常处理（补充）

### 9.1 订单状态机

```text
待支付 -> 已支付 -> 已完成
待支付 -> 支付失败
待支付 -> 已关闭
待支付 -> 待确认收款 -> 已支付
```

- `已支付`触发：微信支付回调成功，或店长确认线下收款成功
- `待确认收款`：仅用于顾客端选择线下付款后的中间状态
- 疗程卡订单：进入`已支付`后状态为“待服务”，每次服务核销后更新剩余次数
- 家居产品订单：进入`已支付`后可直接置为`已完成`

### 9.2 服务单状态机

```text
待服务 -> 服务中 -> 已完成
```

- 只有店长或被分配的服务人员可推进状态
- 仅在`服务中 -> 已完成`时扣减 1 次，且剩余次数不得小于 0
- 重复点击“完成服务”时，后端按同一服务单 ID 幂等处理，不得重复扣次

### 9.3 门店绑定状态机

```text
待审批 -> 已通过
待审批 -> 已拒绝
```

- 同一顾客同一时刻仅一条`待审批`申请
- `已拒绝`后允许重新申请
- 审批全量留痕，便于追溯

### 9.4 异常场景最小闭环

- 重复下单：返回同一订单号，不重复创建订单
- 重复支付回调：仅第一次成功回调生效，不重复入账日历
- 重复线下确认收款：仅第一次确认生效，不重复入账日历
- 网络抖动导致实时推送失败：轮询兜底后保证最终一致
- 并发核销：通过事务或行级锁保证同一疗程卡不会被超扣

## 十、MVP 验收标准（补充）

1. 订单进入`已支付`后，员工端顾客日历在 **5 秒内**出现当日消费标记
2. WebSocket 断开情况下，员工端在 **30 秒内**通过轮询看到同一笔消费
3. 同一笔订单无论重复提交多少次，在日历中仅计入一次
4. 同一服务单重复点击"完成服务"不产生重复扣次
5. 角色越权操作应被拒绝（美容师不可开单、技师不可查看完整手机号）
6. 小程序读取的员工、产品、组织架构数据与 Workfine 设计端一致
7. 小程序中完成开单后，Workfine 对应的销售单表中能查到同一笔记录
8. 小程序中完成营业额分配后，Workfine 对应表中能查到分配明细
